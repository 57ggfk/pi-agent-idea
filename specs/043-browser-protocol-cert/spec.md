# Feature Specification: 内置浏览器协议与证书策略

**Feature Branch**: `release/0.5.10`

**Created**: 2026-11-16

**Status**: Draft（需求已收集、疑问已澄清；只产出 spec，不写 plan/tasks，不实现）

**Input**: 用户提出（2026-11-16，紧接 042 内置浏览器需求）
> 协议安全上支持 HTTP 和不安全的 HTTPS 就是没有证书的。如果也能支持配置更证书更好。

本规格是 **042 内置浏览器的配套基座**（其 P0 预览基座的安全面），专门定义内置 JCEF 页面加载时的 **HTTP / 不安全 HTTPS / 证书配置** 策略。**范围严格限定在内置浏览器（JCEF 页面加载）**——pi 进程、npm registry、provider / MCP 的网络请求与证书策略**不在本规格内**（用户 Q1 明确）。

## 可行性与现状（读码核实）

- **JCEF 宿主**：`PiAgentPanel.kt` 的 `CefRequestHandlerAdapter`（`:83-96`）只实现 `onBeforeBrowse`——非 `127.0.0.1`/`localhost` 的 URL 一律 `BrowserUtil.browse` 转系统浏览器并返回 true 取消导航；**未实现 `onCertificateError` / `getAuthCredentials`**。内置浏览器是 042 要新建的第二个 JBCefBrowser，其请求处理链需独立挂接，不受现有「转系统浏览器」的 linkHandler 影响。
- **本地 UI server**：`LocalUiServer.kt` 走 loopback HTTP，是现有面板的加载源，与内置浏览器的目标页面是两回事，本规格不改它。
- **证书处理缺口**：JCEF 提供 `CefRequestHandler.onCertificateError` 回调（可 continue ignore / cancel），并支持启动参数层级信任（如 Chromium 类的 ignore-certificate-errors / custom CA），具体可用形态**须实现期真机探针确认**（见「待 plan 技术问题」）。
- **配置持久化**：项目已有设置/持久化机制（SettingsPanel + 配置存储），本规格的配置项应沿用现有设置通道，不新造配置体系。

## User Scenarios & Testing

### US1 - 打开 plain HTTP 页面 (P1)
用户在内置浏览器地址栏输入 `http://` 页面（本地 dev server 或内网地址），页面正常加载渲染，不被现有 `onBeforeBrowse` 的「转系统浏览器」逻辑截走，也不因非 https 被拦。

### US2 - 打开自签名 / 无效证书 HTTPS 页面 (P1)
用户访问自签名证书、过期、域名不匹配，或使用内网私有 CA 的 HTTPS 页面——证书错误不会直接白屏；按当前证书策略决定「放行并渲染」还是「显示明确的证书警告页」，行为可预期。

### US3 - 配置证书策略 (P1)
用户在设置里配置以下三种形态（可组合），配置后对内置浏览器页面加载立即/按规则生效：
1. **总开关**：允许不安全证书（开/关）；
2. **信任指定证书文件**：导入 `.crt` / `.pem` CA 文件，仅信任它签发的页面；
3. **按域名白名单**：只对指定 `host[:port]` 放宽校验，其余 host 仍严格校验。
配置持久化，重启 IDE 后仍生效。

### US4 - 安全默认值 (P2)
默认策略为**严格校验**（不放行无效证书）；任何放宽都由用户显式配置触发。公网域名默认不受「允许不安全证书」总开关之外的隐式放宽。界面须让用户清楚当前页面处于「不安全证书已放行」状态。

## Requirements

- **FR-001** 内置浏览器 MUST 能加载 plain `http://` 页面；MUST NOT 被现有 linkHandler 的「非本机 URL 转系统浏览器」规则截获。
- **FR-002** 内置浏览器 MUST 实现 `onCertificateError` 处理，覆盖四类错误：**自签名、过期、域名不匹配、内网私有 CA**；对每类错误按当前策略给出「放行」或「拒绝」的确定行为。
- **FR-003** MUST 提供证书策略配置，支持三种形态且可组合：**(a) 允许不安全证书总开关**、**(b) 信任指定 `.crt`/`.pem` 证书文件**、**(c) 按 `host[:port]` 白名单放宽**。
- **FR-004** 默认 MUST 为严格证书校验；放宽 MUST 由用户显式配置触发，MUST NOT 默认放行。
- **FR-005** 证书错误被放行时，页面 MUST 有可见的「不安全证书已放行」状态提示（如地址栏标识/警告条），避免静默降级。
- **FR-006** 证书策略配置 MUST 沿用项目现有设置/持久化通道，重启后生效；配置变更 MUST 不影响现有面板（本地 UI server）的加载。
- **FR-007** 本规格 MUST NOT 影响 037：外链仍走系统浏览器；MUST NOT 影响 014 OAuth：认证仍走系统浏览器；内置浏览器的证书放宽 MUST NOT 外溢到 pi 进程 / npm / provider / MCP 的网络请求。
- **FR-008** 证书文件路径读取 MUST 做校验（文件存在、格式合法、解析失败时给出错误提示而非崩溃）；放宽规则 MUST 限定 host[:port] 粒度，MUST NOT 用宽泛通配符默认放行全网。
- **FR-009** 本项目遵守中国法律法规与内容安全要求；证书策略仅用于开发者本地/内网开发场景，MUST NOT 用于绕过合法站点的安全校验或访问违法内容。

## Decisions（用户已拍板 2026-11-16）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 适用范围 | **仅内置浏览器（042 延伸）**；pi / npm / provider / MCP 网络请求不动，不建统一网络层 |
| Q2 | 支持哪些证书错误 | **四类全支持**：自签名、过期/域名不匹配、内网私有 CA、完全跳过校验 |
| Q3 | 配置形态 | **三种全要且可组合**：允许不安全证书开关、信任指定证书文件、按域名白名单 |

## 待 plan 阶段决定的技术问题（本规格不锁定）

- JCEF 证书放宽的**具体生效机制**：`onCertificateError` 逐次回调放行 vs 启动参数（ignore-certificate-errors / SPKI 白名单 / 自定义 CA 注入）——哪条在 233–263 全版本可用且能覆盖四类错误，须真机探针确认。
- 「信任指定证书文件」的解析与注入路径：`.crt`/`.pem` → JCEF 可识别的信任锚 / SPKI hash 的具体转换。
- 「按域名白名单」的匹配语义：精确 host:port、是否支持子域、端口省略时的默认匹配。
- 三种形态**组合时的优先级**（如总开关关但白名单命中、证书文件与白名单冲突）。
- 「不安全放行」状态提示的 UI 形态与位置（地址栏徽标 / 页面顶部警告条），以及是否每次导航都提示。
- 配置项在现有设置体系中的落位（新分组还是并入浏览器设置）与数据结构。

> **真机探针记录（2026-11-18，CDP 层）**：在 IDEA 2026.2.3 / JCEF Chrome 144 上，`Security.setIgnoreCertificateErrors` 在页面级 CDP available（`scripts/probe-042-cdp.mjs`，结果 `build/probe-042-result.json`）。
> 但这**只证明 CDP/DevTools 通道**可以切换证书忽略；本规格 FR-002 依赖的是 **JCEF Java 请求处理链的 `CefRequestHandler.onCertificateError` 回调**（内置浏览器独立挂接的那条链），二者是不同层。Java 层回调在四类证书错误下的行为、`getAuthCredentials`、启动参数（ignore-certificate-errors / 自定义 CA 注入）在 233–263 全线的可用性**仍未真机验证**，须在内置浏览器原型落地后单独探针。不得据本条提前判定 FR-002/FR-003 已可实施。

## 不做的事

- 不改 pi 进程 / npm registry / provider / MCP 的网络与证书策略（用户 Q1）。
- 不改 037 外链系统浏览器策略、不改 014 OAuth 系统浏览器认证。
- 不实现完整的 042 内置浏览器（地址栏、导航、DevTools、批注）——本规格只管协议与证书面，是 042 的配套基座。
- 不默认放行任何无效证书；不做「一键永久信任所有证书」的隐式行为。

## 与既有规格/事实的关系

- **042**：本规格是 042 内置浏览器 P0「预览基座」的安全面配套；042 的「URL 安全边界」探针结论应回填本规格。
- **037 / 014**：外链与 OAuth 仍走系统浏览器，证书放宽严格限定在内置浏览器页内。
- **019**：内置浏览器作为新增 JBCefBrowser / Content，须隔离 instance 计数与 token 分桶，不污染 pi 会话（019 硬教训）。
- 合规：遵守中国法律法规与内容安全要求（FR-009）。
