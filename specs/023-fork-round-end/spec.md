# Feature Specification: Fork 以「整轮」为单位 —— 只出现在每轮最后一条 pi 回复上

**Feature Branch**: `release/0.5.7`

**Created**: 2026-11-10

**Status**: Draft

**Input**: 用户反馈（2026-11-10）
> fork 消息应该是保证统一轮次是个整体，那么干脆只在 pi 消息的最后一个加 fork 不就行了，避免误导。

澄清（同轮对话）：用户发一个消息，智能体经过多轮执行（工具调用、再总结），
**Fork 按钮应该只在最后一轮**；末轮怎么复制不重要，「反正就是 fork 功能」。

**难度定位**：小。改动集中在一个动作矩阵的判据 + 一处索引规范化 + 测试同步；
但**语义是真的错了**，不是观感问题——详见下面「三处错位」。

## 问题陈述

「一轮」= 用户一次提问 + 该轮 pi 产生的**全部**回复。一轮里 pi 往往不止一条回复：
先回一条带工具调用的，工具跑完再回一条总结。界面上这是两条独立的 pi 消息。

而 pi 的分叉原语是 `fork {entryId}`，其中 `entryId` **只能是用户消息**，语义是「在**该用户消息之前**切开」。
所以一轮内任意一条 pi 回复点 Fork，落到 pi 侧都是同一个动作：**在下一条提问之前切开**。
（协议事实见 `specs/007-message-fork/fork-semantics.json`，对 pi 1.5.0 实测。）

于是现在「每条 pi 回复都有 Fork」产生了三处错位：

| # | 现象 | 用户看到什么 |
|---|---|---|
| 1 | 同一轮里每条回复都有 Fork，点哪条结果都一样 | 以为能「从工具调用那条岔开」，实际不行 |
| 2 | 中间那条点下去，**同轮后面的回复照样带入** | 确认框写着「其后的内容不会带入」，结果带入了 |
| 3 | 单轮会话点中间那条，pi 侧没有「下一条提问」可切，**退化成整条复制** | 确认框写着「新会话以这条回复结尾」，结果整条复制 |

其中 2 直接违反 007 的 **FR-003**（「新会话 MUST NOT 包含该回复之后的消息」）——
该条只在「本轮最后一条」上成立，在中间回复上是假的。

### 现在的入口分布（以本仓库 mock 为对照）

mock 一次提问固定产出 **2 条** pi 回复（先工具调用、后总结），因此：

```
[U1] [A1: 带 bash/edit 工具调用] [A2: 总结]
       ↑ Fork 出现在这里          ↑ Fork 也出现在这里
       点下去 = 整条复制（单轮无后继提问）      点下去 = 整条复制
       ↑ 确认框却说「以这条回复结尾，其后的内容不会带入」
```

真实会话里工具调用轮数更多，误导面更大。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每轮只在末尾露出一个 Fork (Priority: P1)

用户发一个问题，智能体调用了几次工具、最后给出总结。鼠标扫过这一轮里每一条 pi 回复时，
**只有最后那条**带 Fork；中间那几条只有复制/引用。

**Why this priority**: 这是本次反馈的原话诉求；同时消掉「同一条结果、多个入口」的误导。

**Independent Test**: 造一轮（U1 + A1 工具调用 + A2 总结），断言 A1 的工具条无 Fork、A2 有 Fork；
再造第二轮（U2 + A3 + A4），断言 A2 重新有 Fork（因为它成了第一轮的末尾）、A3 无 Fork。

**Acceptance Scenarios**:

1. **Given** 一轮有 A1（工具调用）与 A2（总结），**When** 依次悬停两条回复，**Then** 只有 A2 出现 Fork，
   A1 只有复制与引用。
2. **Given** 会话有两轮（U1/A1/A2、U2/A3/A4），**Then** Fork 恰好出现在 A2 与 A4 上，共 2 个入口。
3. **Given** 会话只有一轮，**Then** Fork 只出现在最后那条回复上，共 1 个入口。
4. **Given** 某轮以系统错误消息结尾（如重试提示、上下文压缩通知），**Then** 该轮的 Fork 仍在
   该轮最后一条 **pi 回复**上，不被系统消息顶掉。

### User Story 2 - 从非末尾回复触发，也按整轮算 (Priority: P1)

即使 Fork 由「本轮中间那条回复」触发（旧版本入口、自动化脚本、将来新加的位置），
结果也必须与本轮末尾那条完全一致 —— 不出现「只保留半轮」的会话。

**Why this priority**: 用户的原话是「保证统一轮次是个整体」。把这条做成结构性保证，
才不至于下次加新入口时又漏掉；只靠隐藏按钮是「看不见就没错」。

**Independent Test**: 直接以 A1（中间回复）触发 Fork，断言新会话与以 A2 触发产生的新会话逐条一致，
且 A1 之后的同轮回复仍在（不会出现「A1 之后被截掉」的会话）。

**Acceptance Scenarios**:

1. **Given** 一轮 U1/A1/A2 且其后还有 U2，**When** 以 A1 触发 Fork，**Then** 新会话含 U1/A1/A2 全部内容，
   U2 及其之后不在新会话中。
2. **Given** 同上，**When** 分别以 A1、A2 触发 Fork，**Then** 两次结果的会话内容一致。

### User Story 3 - 中间回复的工具条保持完整 (Priority: P2)

去掉 Fork 后，中间那条回复的悬停工具条不应变空、置灰或留占位；复制与引用照旧。

**Why this priority**: 这是「完全不渲染」的具体化；也防止把「隐藏一个按钮」做成「整排消失」。

**Independent Test**: 悬停中间那条回复，断言工具条可见，且只含复制与引用两项，无灰态、无占位。

**Acceptance Scenarios**:

1. **Given** A1 是中间回复，**When** 悬停，**Then** 工具条出现，按钮为复制、引用两项。
2. **Given** A1 只含图片没有文字，**When** 悬停，**Then** 工具条为空（无复制/引用可做，也无 Fork），
   不出现空壳容器。

### User Story 4 - 末轮行为不变 (Priority: P2)

会话最后一轮（之后没有新提问）的 Fork 仍等价于「整条复制到新会话」，确认框文案不改。

**Why this priority**: 用户明确「不管怎么复制，反正就是 fork 功能」；这条只用来锁定「不要顺手改掉」，
避免实现阶段自我发挥。

**Independent Test**: 单轮会话悬停末尾回复点 Fork，断言新会话逐条等于旧会话，确认框文案与当前一致。

**Acceptance Scenarios**:

1. **Given** 会话只有一轮，**When** 对末尾回复点 Fork 并确认，**Then** 新会话与旧会话消息逐条一致，旧会话不变。
2. **Given** 会话有后续提问的轮次，**When** 对其中间轮次的末尾回复点 Fork，**Then** 确认框文案
   「其后的内容不会带入」与实际结果一致（后续轮次确实不在新会话里）。

## Requirements *(mandatory)*

- **FR-001**: 一轮（一次用户提问 + 该轮产生的全部 pi 回复）中，Fork MUST 只出现在该轮**最后一条** pi 回复上；
  同轮的其他 pi 回复 MUST NOT 提供 Fork。
- **FR-002**: 「本轮最后一条 pi 回复」定义为：该回复之后、下一条用户消息之前，不存在其他 pi 回复。
  若该轮之后没有新的用户提问，则该轮最后一条 pi 回复即整个会话的最后一条 pi 回复。
- **FR-003**: 用户消息与系统消息（普通通知、错误提示）MUST NOT 提供 Fork（沿用 007 FR-001）。
- **FR-004**: 以**非末尾** pi 回复触发 Fork 时（旧入口、自动化、将来新增入口），行为 MUST 与本轮末尾那条一致；
  MUST NOT 产生「只保留半轮」或「截断在同轮中间」的会话。
- **FR-005**: 非末尾 pi 回复的工具条 MUST 保持可见，并 MUST 仍提供复制与引用；
  MUST NOT 因移除 Fork 而置灰、留空位或整排消失。
- **FR-006**: 会话最后一轮（无后续提问）的 Fork 行为 MUST 保持现状（等价整条复制），
  其确认框文案 MUST NOT 因本次改动而变化。
- **FR-007**: 作为 Fork 目标的回复若正在流式中、或会话忙（有运行中任务）、或上方没有任何用户消息，
  MUST NOT 提供 Fork（沿用 007 FR-002 与 007 边界条款）。
- **FR-008**: 本次改动 MUST NOT 影响复制、引用、重新生成、编辑四项动作的可用性判据。

**交付要求（非功能行为，但必须做到）**

- 既有自动化测试里凡以「本轮第一条/中间条」定位 Fork 的用例，MUST 同步改为定位本轮末尾，
  MUST NOT 通过放宽断言、改成「至少 1 个」之类掩盖本次语义变更。

## 验收口径

| 编号 | 检查项 | 期望 |
|---|---|---|
| A1 | 一轮 3 条 pi 回复 | Fork 恰好 1 个，在本轮末尾 |
| A2 | 会话 3 轮（每轮 2 条 pi 回复） | Fork 恰好 3 个，分别在各轮末尾 |
| A3 | 中间回复悬停 | 工具条在，含复制+引用，无 Fork |
| A4 | 以中间回复触发 Fork | 与以末尾触发结果一致，同轮后续回复不被截掉 |
| A5 | 末轮末尾 Fork | 整条复制，旧会话不变，文案不变 |
| A6 | 流式中 / 会话忙 | 任何 pi 回复都不出现 Fork |
| A7 | 无前置用户消息的回复 | 不出现 Fork |
| A8 | 覆盖既有测试 | 全部通过，且断言指向明确的那一条回复（不是「至少有」） |

## 对 007 的修订

| 007 条款 | 原文 | 本次 |
|---|---|---|
| FR-001 | 「**每条** pi（assistant）消息的悬停工具条 MUST 提供 Fork 动作」 | 改为「**每轮最后一条** pi 回复」；同轮其余回复不提供。007 已发布，实现按其原文会回归本次结论，实现时以本文为准 |
| FR-003 | 「新会话 MUST 包含该回复及其之前的全部上下文，MUST NOT 包含该回复之后的消息」 | 条款不变，但**从此无条件成立**；改动前它在同轮中间回复上是假的 |
| US1 独立测试 | 「造 4 轮对话（U1/A1/U2/A2），悬停 A1 点 Fork」 | 仍然成立：A1 后面跟着 U2，属于本轮末尾 |
| FR-004 | 「对最后一条 pi 回复 Fork 等价于复制整个会话」 | 不变（本文 FR-006 明确保留） |

## 非目标

- **不做「半轮 Fork」**：pi 的分叉原语只接受用户消息作为切点，无法切在两条 pi 回复之间。这是协议限制，不是取舍。
- 不改「重新生成」「编辑重发」的入口与判据。
- 不改 Fork 的确认框文案、错误提示、标题后缀（`(fork)`）。
- 不改 `clone` 与 `fork` 的选择逻辑本身（分支点仍按「下一条用户提问」计算）。
- 不改底部控制栏 Fork 的隐藏状态（007 FR-006）。

## 待确认 / 已知风险

- **插话（steer）与用户消息计数的对齐**：Fork 的分支点用「本地 transcript 里的用户条目数」对齐 pi 的
  `get_fork_messages` 长度。插话会产生一条「先渲染、下次重放时才消失」的临时用户条目，
  理论上会让两侧计数错位一位（错位后可能岔到相邻轮次，或提前退化成整条复制）。
  线上是否真会发生取决于 pi 回写该用户消息的时序（本仓库实现里靠「文本相同即去重」兜住）。
  本次**不扩大改动范围**，但要求实现阶段用一条可复现的用例测一次；确认有问题再单独立项。
- **多实例（019）之后**：「本轮末尾」是纯 UI 层判定，与实例无关；019 落地时不需要重算。
