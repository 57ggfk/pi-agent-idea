# Feature Specification: 注入内容统一收尾换行规则

**Feature Branch**: `release/0.5.10`

**Created**: 2026-11-17

**Status**: Implemented（已实现并随 0.5.10 内测；发布文案见 changelog.d/045-*）

**Input**: 用户提出（2026-11-17，044 折叠光标问题延伸）
> 粘贴大段文本希望能自动追加额外的换行，包括添加多行引用也追加换行，添加单行引用则追加 2 个空格。

## 一、意图与边界（用户已确认 2026-11-17）

用户拍板两条：
1. **作用范围 = 所有注入内容**：不只 044 的粘贴折叠，还包括编辑器引用（quote 注入）、文件引用（`@path`）等所有"把一段内容注入到输入框"的通路，统一同一套收尾规则。
2. **收尾规则**：注入内容是**多行** → 追加一个换行 `\n`；是**单行** → 追加两个空格（Markdown 硬换行语义）。目的：让注入块与用户后续输入之间有清晰分隔、光标可见可继续编辑（直接回应 044 #2a「折叠后看不到光标」）。

本规格只定义**收尾字符与适用范围**，不改动各注入通路自身的内容生成、发送还原（如 044 的 `expandPastes`）或语法高亮。

## 二、可行性与现状（读码核实）

- **注入通路盘点**（均汇入 `pendingPrompt` / `Composer.tsx` 的 `applyText`，是统一收口点）：
  - 粘贴折叠：`foldPastedText`（`Composer.tsx:434-457`）插入折叠 token，光标落在 token 尾部。
  - 编辑器引用 / quote：`pendingPrompt.mode === "quote"` 分支已用 `withNewline(s) = s.trimEnd() + "\n"`——当前**只有**追加 `\n` 一种行为，不区分单行/多行，也不加双空格（025 spec 现状记录）。
  - 文件引用：018/015 插入 `@path` token（镜像层药丸），路径 token 后通常已带空格。
  - 拖拽文本、skill 引用等：经 `pendingPrompt` 的其它 mode。
- **关键风险——重复叠加**：若在每个通路各自写收尾，会让"本来已带 `\n`/空格的内容"再叠一层，出现多余空行 / 行尾多余空格，且 `trimEnd()` 会破坏代码/ Markdown 结尾有意义的空白。
- **发送完整性不受影响**：044 走 `expandPastes` 还原原文、pi 收到完整内容；收尾字符属于草稿可见文本的一部分，需确认是否随发送带入（见待拍板技术项）。

## 三、User Scenarios & Testing

### US1 - 多行注入追加换行 (P1)
用户粘贴/引用一段多行内容（>1 行）到输入框，注入块之后自动有一个换行，光标落在下一行行首，用户可立即接着输入说明，注入块与说明不粘连。

### US2 - 单行注入追加双空格 (P1)
用户粘贴/引用一段单行内容（1 行），注入块之后自动追加两个空格（Markdown 硬换行），光标在两个空格之后，视觉上与后续文本分行但仍属同一段。

### US3 - 各通路一致 (P1)
粘贴折叠、编辑器引用、文件引用等所有注入通路都遵循同一收尾规则，用户不需要记住"哪个通路会多换行、哪个不会"。

### US4 - 零重复叠加 / 零回归 (P1)
内容本身已以换行或空格结尾时不重复叠加；原有 Markdown 渲染、代码块、镜像层药丸、发送还原（FR-007）全部零回归。

## 四、Requirements

- **FR-001** 所有注入内容通路 MUST 在注入块之后按统一规则追加收尾：**多行内容追加 `\n`，单行内容追加两个空格**。
- **FR-002** 收尾规则 MUST 在 `pendingPrompt`/`applyText` 的统一收口点实现一次，MUST NOT 在各通路各写一份；各通路只提供"注入的原始内容 + 行数信息"。
- **FR-003** 追加前 MUST 检测内容末尾已有的空白：已含等价收尾（多行已有 `\n`、单行已有 ≥2 空格）时 MUST NOT 重复叠加；不得对内容中部或代码/代码块内部空白做 trim。
- **FR-004** 收尾追加后 MUST 把光标定位到注入块收尾之后（可见、可继续输入），不破坏 018 镜像层药丸/选中/IME（044 FR-008、010 自适应）。
- **FR-005** 收尾字符 MUST NOT 破坏发送完整性：pi 收到的正文与用户所见一致，044 折叠内容仍由 `expandPastes` 完整还原（044 FR-007）。
- **FR-006** 本规则 MUST NOT 回归现有 quote/文件引用/拖拽/skill 注入行为；已带自己收尾的通路（如文件引用 token 后的空格）按 FR-003 判重后一致化。

## 五、Decisions（用户已拍板 2026-11-17）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 作用范围 | **所有注入内容统一**（粘贴折叠、编辑器引用 quote、文件引用等），不是只有 044 |
| Q2 | 收尾规则 | 多行 → `\n`；单行 → 两个空格（Markdown 硬换行） |
| Q3 | 是否新增 spec | 独立 spec 045，与 044 解耦（044 只要求"折叠后光标可见"，收尾字符归本规格） |
| Q4 | 版本 | 全部进 0.5.10（随 044 一起交付） |

## 六、待 plan 阶段决定的技术问题（本规格不锁定）

- 收尾字符是否随发送进入 pi 正文，还是仅作草稿可见分隔、发送前剥离——需结合 044 `expandPastes` 与 quote 现状确认，避免 pi 收到多余空行/空格。
- "多行"判定口径：按换行符数（>0 即多行）还是按渲染行数。
- 单行双空格与 Markdown 行尾语义的兼容（若内容本身是要被当代码发送，双空格是否多余）。
- 判重策略：末尾已有空白时"不叠加"的等价判定，是否区分 `\n` 与空格。
- 各通路的"行数信息"如何传给统一收口点（统一计算 vs 调用方提供）。

## 七、不做的事

- 不改各注入通路的内容生成逻辑与文案。
- 不改 044 的 `expandPastes` 还原与 018 的镜像层 token 渲染。
- 不改 Markdown 渲染（039/040）与 IDE 打开（041）。

## 八、与既有规格的关系

- **044**：解决 #2a「折叠后光标不可见」的收尾字符由本规格统一定义；044 保留"光标可见"的行为要求。
- **025**（注入后自适应并滚到末尾）：收尾追加属于"内容变多"，需复用 025 的 `autosizeAndReveal` 保证输入框长高并停在末尾。
- **018/015**：文件引用 token 的收尾判重按 FR-003 处理，避免重复空格。
- **041**：代码块「在 IDE 打开」不属"注入到输入框"通路，不受本规则约束。

## 开放问题

无阻塞项。范围（全部通路）、规则（多行 `\n` / 单行两空格）、独立 spec、版本（0.5.10）均已拍板；收尾是否随发送、判重细节留 plan 阶段决定。
