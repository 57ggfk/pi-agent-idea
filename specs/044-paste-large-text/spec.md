# Feature Specification: 粘贴大段文字优化（折叠占位 + 另存文件引用）

**Feature Branch**: `release/0.5.10`

**Created**: 2026-11-16

**Status**: Draft（需求已收集、疑问已澄清；只产出 spec，不写 plan/tasks，不实现）

**Input**: 用户提出（2026-11-16）
> 粘贴大段文字的优化，参考效果：pasted Markdown (2.686 lines)

参考的是 Claude Code / Codex 等工具的做法：粘贴超阈值文本时输入框内折叠为占位 chip（如 `pasted Markdown (2,686 lines)`），输入框保持紧凑，**完整内容照常发送**。

本规格提供**两条互补路径**（用户 2026-11-16 追加拍板，分层结合）：
1. **默认路径——折叠 chip**：粘贴即折叠，内容随文本发送（FR-001~010）。
2. **另存文件引用路径**：超大内容或用户主动时，把粘贴文本写为系统临时目录下的文件，插入 `@path` 引用——pi 在发送时读取文件全文（FR-011~014）。

## 可行性与现状（读码核实）

- **当前粘贴路径**：`web/src/components/Composer.tsx:920-941` 的 `onPaste` —— 图片 → 附件 chips；单个文件路径 → `@path` 引用 token（015/018）；**纯文本（含多行 Markdown）→ 不拦截，走浏览器默认插入，整段塞入 textarea**。
- **textarea 是纯文本**：`:897-911` 用 `<textarea>` + `value={text}`，`autosize` 随内容撑高——大段粘贴会把输入框撑到极高，把用户自己写的提示词挤出视野（正是参考效果要解决的问题）。
- **已有镜像层可复用**：`composer-mirror`（`:890-896`，018 US1）是一层覆盖在 textarea 上的非交互镜像，专门用来在原始文本上画 token 药丸。折叠 chip 的渲染可沿用这套「原文在 textarea、视觉在 mirror」的思路，但 chip 需要可交互（点击/hover），与现有 mirror 的 `aria-hidden` 非交互语义不同——实现期须决定是扩展 mirror 还是另设 chip 层。
- **发送语义无需改**：`send()`（`:529`）把 `text` 原样作为 body 送出。折叠只要保证「textarea 内的真实文本仍是完整原文」（或发送时还原完整内容），发送侧天然满足完整性。
- **反面教训（调研所得）**：Claude Code 的高赞 issue 是「折叠后无法查看/复制回原文、从 transcript 复制出的只是占位符」。故本规格把「查看/展开通道」列为硬要求（FR-004/005/006），不做只能折叠不能读的单向优化。

**另存文件引用路径的读码核实（用户追加需求）**：
- **`@path` 是内容引用而非路径标记**：前端只插入 `@path ` token，**pi 在发送时自己读取被引文件的内容**（`BridgeService.kt:1187` 注释、`store.ts:1694` 的 `resolveRefs` → `files.relpath`）。所以引用临时文件 = pi 拿到全文，发送完整性天然满足，与折叠路径一致。
- **无现成「文本 → 临时文件」桥接**：现有 `files.takeDrop` / `files.relpath` 只处理已存在文件路径；写盘能力项目内普遍（`PiCredentials.kt:195` 等 `Files.write` / atomic move），但需**新增一个 RPC**：接收文本 → 写到系统临时目录 → 返回可被 `@path` 引用的路径。
- **Claude Code 的定位佐证**：官方文档把「存成文件 + `@filename`」列为**避免折叠的建议做法**，与折叠互补——印证分层结合合理。
- **已知代价（必须正视）**：用户选择「系统临时目录 + 会话级清理」，则**历史会话中的 `@path` 在文件被清理后会断链**（拿不到原文）——这与 Claude Code paste-cache 的过期坑同源。缓解见 FR-014（断链不得静默、须明确提示，且不覆盖折叠路径的永久可追溯）。

## User Scenarios & Testing

### US1 - 大段粘贴自动折叠 (P1)
用户复制一段日志 / Markdown / 代码（>3 行或 >800 字符）粘贴到输入框，输入框内不铺开全文，而是显示一个占位 chip，形如 `pasted Markdown (18 lines)`（标签按内容类型识别，行数用本地化数字格式）；用户自己先打的提示词仍完整可见，输入框不被撑高。

### US2 - 展开查看/编辑 (P1)
用户点击 chip，折叠内容在输入框内内联展开为完整原文，可移动光标、删改、再折回；用户随时能确认「到底要发给模型什么」，避免盲发。

### US3 - hover 预览 (P2)
用户不点击、仅把鼠标悬停在 chip 上，浮层展示粘贴内容预览（只读），快速判断粘贴对错，不改变输入框状态。

### US4 - Shift+粘贴临时不折叠 (P2)
用户按住 Shift 粘贴时，本次跳过折叠，全文直接插入输入框——给「这次我就是要看全文」的场景一个明确手势。

### US5 - 发送完整性 (P1)
无论折叠与否，提交时 pi 收到的都是**完整原文**，不是占位文本；已发送的消息历史里，用户粘贴的内容可完整查看、可复制回原文（不复蹈 Claude Code 的 transcript 折叠坑）。

### US6 - 短粘贴不受影响 (P2)
低于阈值的粘贴（≤3 行且 ≤800 字符）保持现状直接插入；图片、文件引用粘贴行为零回归（018 US3 语义不变）。

### US7 - 另存为文件引用 (P1)
用户在大段粘贴产生的 chip 上点「存为文件」，或粘贴内容超过更大阈值（如 2000 行）时收到自动提示可选择——系统把这批文本写到临时目录的文件，并在输入框插入 `@path` 引用（替换原折叠 chip）。pi 发送时读取文件全文，用户得到「引用一个可打开查看的大文件」的体验，而不是一坨折叠文本。该文件在会话级生命周期结束时清理。

### US8 - 文件引用断链可感知 (P2)
当用户回看一个历史会话、其中的临时文件引用已被会话级清理时，UI **不得静默显示空的/失效的 `@path`**——须明确提示「该临时文件已清理」，且不得把占位文本当作原文发给 pi；用户仍能区分「折叠路径」（内容永久在消息里）和「文件引用路径」（依赖临时文件存活）。

## Requirements

- **FR-001** 纯文本粘贴 MUST 在超过阈值时折叠为占位 chip；阈值默认 **>3 行 或 >800 字符**（任一满足即折叠，与主流工具一致）。
- **FR-002** 阈值判定 MUST 基于粘贴内容本身（行数 = 换行符数 + 1 的语义、字符数），在 `onPaste` 阶段同步完成；短粘贴 MUST 走原默认插入路径。
- **FR-003** chip 标签 MUST **按内容识别类型**并显示行数：如 `pasted Markdown (18 lines)` / `pasted JSON (…)` / `pasted code (…)` / 识别不出则 `pasted text (…)`；类型识别规则须在实现期明确并写进 plan（可先从轻量特征判断起步，不引入重型语言检测依赖）。行数显示 MUST 本地化（中文直接数字如 `18 行`；参考里的 `2.686` 是德语千分位，中文不用点分位）。
- **FR-004** 折叠 MUST 保留完整原文，且 MUST 提供**点击 chip 内联展开/收起**能力，展开后原文可查看、可编辑、可复制。
- **FR-005** chip MUST 支持 **hover 只读预览浮层**，展示粘贴内容（可限制预览长度，超出省略并提示展开）。
- **FR-006** MUST 支持 **Shift + 粘贴**跳过折叠、直接插入全文的临时手势。
- **FR-007** 提交时 pi MUST 收到完整原文（非占位文本）；**已发送消息历史中用户粘贴的内容 MUST 可完整查看与复制**，不得只显示占位符或不可展开的折叠文本。
- **FR-008** 折叠实现 MUST NOT 破坏 textarea 的光标 / 选区 / IME 输入法行为，也不得破坏 018 的镜像层 token 药丸与文件引用（015）——折叠态与展开态切换须保持输入可用性。
- **FR-009** 折叠/展开/预览的文案 MUST 走 i18n（zh/en），MUST NOT 硬编码；chip 须有合适的 `data-testid` 供 e2e 断言。
- **FR-010** 图片粘贴 → 附件、文件路径 → `@path` 引用的既有语义 MUST 零回归（018 US3）。

**另存文件引用路径（FR-011~014）**

- **FR-011** chip MUST 提供「存为文件」操作；粘贴内容超过更大阈值（默认 **2000 行**，实现期可调）时 MUST 给出「另存为文件引用」的提示（非强制，用户可选）。
- **FR-012** 另存 MUST 新增桥接：接收粘贴文本 → 写入**系统临时目录**下的文件 → 返回可被 `@path` 引用的路径，并据此插入引用 token（替换原折叠 chip）。pi 发送时读取文件全文，MUST 保证模型收到完整内容。
- **FR-013** 临时文件生命周期为**会话级**：会话结束/清理时删除对应临时文件；写入与清理 MUST 有错误兜底（写失败须保留折叠路径不丢内容，清理失败不得影响会话使用）。
- **FR-014** 因会话级清理导致历史会话中的临时文件引用断链时，UI MUST **明确提示「临时文件已清理」**，MUST NOT 静默把失效 `@path` 或占位文本当作原文提交；本路径的「非永久可追溯」是已接受的已知代价，MUST NOT 影响折叠路径（FR-007）的永久可查看/可复制保证。

## Decisions（用户已拍板 2026-11-16）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 折叠阈值 | **行数或字符数双阈值**：>3 行 或 >800 字符任一满足即折叠；短粘贴原样插入 |
| Q2 | 查看/展开方式 | **点击 chip 展开/收起** + **hover 预览浮层** + **Shift+粘贴临时不折叠**（三者都要；未选「再次粘贴展开」） |
| Q3 | 类型标签 | **按内容识别类型**（Markdown/JSON/代码/日志…），识别不出则 pasted text；行数本地化显示 |
| Q4 | spec 组织 | **独立 044 spec**，与 036–043 并列 |
| Q5 | 临时文件 vs 折叠 | **分层结合**：默认折叠 chip，额外提供「另存文件引用」出口——二选一变互补 |
| Q6 | 临时文件位置与清理 | **系统临时目录 + 会话级清理**；接受历史 `@path` 断链代价（FR-014 缓解） |
| Q7 | 另存触发方式 | **chip 上「存为文件」按钮 + 超大内容（如 >2000 行）自动提示**；非强制自动落盘 |

## 待 plan 阶段决定的技术问题（本规格不锁定）

- **折叠态的数据模型**：textarea 里放「占位文本」还是「原文 + 视觉层折叠」？前者发送时需还原、且選中/光标要特殊处理；后者要扩展 mirror 层使其可交互（现有 mirror 是 `aria-hidden` 非交互）。实现期权衡后定，须满足 FR-007/008。
- **内容类型识别规则**：用什么轻量特征判定 Markdown / JSON / 代码 / 日志（如 JSON 以 `{`/`[` 起且可解析、Markdown 含标题/列表/代码围栏特征、代码含常见语法 token）；是否允许误判；不引入重型依赖。
- **行数/字符数统计口径**：截断的换行、CRLF、超长单行如何计。
- **hover 浮层的呈现**：浮层内容长度上限、定位（避免被输入框裁剪）、键盘可达性。
- **Shift+粘贴的事件判定**：JCEF 下 `clipboardData` 是否能可靠读到修饰键状态（若无，需替代手势）。
- **发送历史里的完整原文存储**：是否随消息持久化原文，折叠展示但可展开/复制（关联 FR-007，可能影响 store 数据结构）。
- **autosize 交互**：折叠态输入框高度如何稳定（不因 chip 渲染跳动）。
- **另存 RPC 契约**：接收文本 → 临时文件的桥接方法签名、临时文件命名规则、返回路径的 `@path` 引用格式（绝对/相对）。
- **会话级清理的挂载点**：会话删除/切换/IDE 退出时哪个事件触发清理，如何避免误删仍被引用的文件；写失败/清理失败的兜底策略（FR-013）。
- **超大阈值提示的交互**：>2000 行时提示的形态（chip 上角标 / 单独提示条）与是否可记住选择不再提示。
- **断链检测与提示**：历史会话加载时如何判断临时文件引用已失效（FR-014），提示文案与是否提供「重新粘贴原文」的补救。

## 不做的事

- 不改发送语义（pi 收到的仍是完整文本），不做内容压缩/截断/摘要。
- 不引入重型语言检测/语法识别依赖；类型识别以轻量特征为起点。
- 不做「再次粘贴相同内容展开」（用户未选）。
- 不改图片/文件粘贴逻辑（018/015 保持）。
- 另存文件**不写入项目目录**（用系统临时目录，不污染工作区/git status）；不做自动静默落盘——另存须由 chip 按钮或超大提示触发、用户可选。

## 与既有规格/事实的关系

- **018 US1**：`composer-mirror` 镜像层是折叠 chip 渲染的潜在落点，但需处理其非交互语义。
- **018 US3 / 015**：文件路径 → `@path` 引用的粘贴语义必须保持（FR-010）。
- **003 安全净化**：粘贴内容仍按现有消息发送链路处理，不新增注入面；chip 标签与预览内容须经 React 转义，不 `dangerouslySetInnerHTML`。
- **015/018 `@path` 基建**：另存路径复用现有 `@path` 引用 token 与镜像层药丸渲染（`insertRefTokens` / `resolveRefs`），仅新增「文本落临时文件」的桥接；pi 发送时读文件的语义已由宿主实现，前端不需改发送逻辑。
- **041**：另存的临时文件可在 IDE 中打开查看（若 041 实现），两规格在此处自然衔接，但不互为依赖。
- 与 037/038-043 无耦合——输入框优化 + 一个独立写临时文件 RPC，独立可验。

## 开放问题

无阻塞项。阈值/展开方式/类型标签/spec 组织，以及追加的临时文件三问（分层结合 / 系统临时目录+会话清理 / chip 按钮+超大提示）均已于 2026-11-16 拍板；折叠态数据模型、类型识别规则、另存 RPC 契约与清理挂载点留待 plan 阶段决定。
