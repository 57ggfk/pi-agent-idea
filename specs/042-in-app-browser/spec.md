# Feature Specification: 应用内浏览器（方向性记录 / Direction）

**Feature Branch**: `release/0.5.10`

**Created**: 2026-11-16

**Status**: Draft — **方向性 spec**。本次只记录愿景、竞品画像、能力分层、架构契合与探针清单；**不拆 plan/tasks、不实现、不锁定技术方案**。后续按能力分层逐条另立可实施 spec。

**Input**: 用户提出（2026-11-16，「内置浏览器需求」，经澄清）
> 内置浏览器需求。
> 主要就是做一些预览和开发交互的作用，让那多数的 ai 编程工具内置浏览器的作用，将来还要增加一些更多的交互，比如说要打开开发者工具，还有在页面上实时添加评论啥的，能添加到会话。可以探索一下 codex APP 等主流工具的功能，先不做过深探索，只是记录方向。

## 一、意图与边界（用户已确认）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 用途 | **本地 HTML 预览 + 通用浏览器页签 + 网页外链（不跳出 IDE）** 三者都要；核心是「预览 + 开发交互」，对标主流 AI 编程工具的内置浏览器 |
| Q2 | 与 037 关系 | **037 不动**——市场链接继续走系统浏览器；本能力是独立新能力，外链默认仍走系统浏览器，除非用户主动在浏览器页签打开 |
| Q3 | 承载形态 | **工具窗页签 + 编辑器呈现**都要（用户「如果可以的话最好是这样」）；URL 地址栏须可展示、可编辑 |
| Q4 | 未来交互 | 开发者工具、页面实时批注并**添加到会话**；后续还会更多——本 spec 只记录方向，不穷举 |

## 二、竞品画像（轻量调研，公开资料，2026-11-16）

> 目的：确认方向、校准术语与能力分层，**不是**深度竞品分析；细节以实现期实测为准。

| 工具 | 内置浏览器能力 | 明确边界（可借鉴的取舍） |
|---|---|---|
| **Codex App**（2026-04 起） | 应用内浏览器渲染 localhost dev server / 本地 HTML / 公开 URL；用户直接**在页面上留言**给精确指令；提交批注时自动带**截图 + 相关 DOM 元素**给 agent，形成 build→render→annotate→fix 闭环 | 官方明确**不支持**认证流程、登录态页面、cookie、扩展、用户现有浏览器 profile；定位是「未认证前端的验证面」而**非通用浏览器**，并计划逐步扩展到完整浏览器控制 |
| **Cursor Design Mode / Annotate**（3.24.18+） | 内置浏览器（Agents Window）中点选元素 / Shift 多选 / 框选区域 / 画笔·椭圆·矩形·箭头 / 就地改文字 / CSS 检查器 / 语音；批注随附 tag、id、class、选择器路径、前 200 可见字符、尺寸位置、6 项计算样式 + 裁剪截图；React/Vue/Svelte 带组件名与组件栈；Batch edits 与「加入 chat 输入框」 | 官方自述适合**样式级微调**（间距/字号/颜色/断点/对齐），不适合新建组件、后端逻辑、架构变更 |
| **VS Code 浏览器工具** | 集成浏览器 + `Add to Chat`（Comment on Elements / Share with Agent）；agent 可自主导航交互验证；元素/截图/控制台日志可加到提示 | agent 开的标签用**隔离临时存储**，不继承登录态；需显式批准才能分享标签页；有 enterprise policy / 域名过滤 |
| **华为云码道 Doer IDE** | 地址栏输入网址预览；选中元素 → 加入对话 / 直连智能体 / 样式设置；控制台日志可复制到聊天；拖拽式元素移动；设计与 CSS 双向编辑；元素级评论；HTML 文件右键「在浏览器中预览」 | 国内产品，交互范式与用户描述高度一致，可作「地址栏 + 元素批注 + 日志进会话」的直接参照 |

**归纳出的方向共识**：① 内置浏览器是「渲染结果的验证/反馈面」，不是替代系统浏览器；② 差异化在**批注回流会话时携带的结构化上下文**（元素选择器 + 样式 + 截图），而非纯文本描述；③ 登录态/个人信息场景普遍主动回避（隔离存储或未认证限制）。

## 三、现状与架构契合（读码核实）

- **已有 JCEF 基座**：`PiAgentPanel.kt:331` 的 `JBCefBrowser` 加载本地 web server（`:59` `browser` 字段）；`CefRequestHandlerAdapter.onBeforeBrowse`（`:83-96`）把非本地 URL 转 `BrowserUtil.browse` 系统浏览器——这是 037 修复所依赖的通路，**本能力不改它**。
- **多实例基建可复用**：019（C3 多实例）已实现「一个工具窗多个 Content、各自独立 JBCefBrowser / pi rpc / 事件桶」。浏览器页签可沿用这套 Content 管理，但**页面 token 与 instance 分桶语义需隔离**，避免浏览器页签干扰 pi 会话实例计数（019 的两条硬教训）。
- **桥接通道**：`BridgeService.kt` 有 `ide.openFile` / `ide.showFileDiff` / `ide.openTerminal` 等现成方法；浏览器页签的 URL 导航、批注回流可走同类 bridge 扩展（具体方法签名留给实施 spec）。
- **会话注入**：pi 消息经现有 Composer / 队列通路发送；"批注添加到会话"应复用该通路（与 041「代码块在 IDE 打开」同属「UI → 会话/IDE」出口族），**不新造一套消息通道**。
- **缺口**：前进后退/地址栏/控制台/DevTools/元素选取/截图/批注覆盖层/跨域与 CSP 处理——当前**全部没有**，属于新建能力。

## 四、能力分层路线图（后续逐层另立 spec，本 spec 不承诺排期）

| 层 | 能力 | 说明 |
|---|---|---|
| **P0 预览基座** | URL 地址栏（展示 + 可编辑）、前进/后退/刷新、工具窗页签 + 编辑器呈现、打开 localhost / 本地 HTML / 公开 URL、与 037 并存的外链策略 | 先有「能看、能导航、能进会话」的浏览器壳；这是后续一切交互的地基 |
| **P1 开发交互** | 开发者工具（DOM/控制台/网络，形态待探针）、控制台日志查看与复制进会话、视口/响应式切换、截图 | 对标 Codex / Doer 的「验证面」；JCEF 对 DevTools 的支持方式是实现期探针重点 |
| **P2 批注回流** | 元素点选/框选、批注叠加层、批注附结构化上下文（选择器 + 元素信息 + 计算样式 + 裁剪截图）、批量发送、**添加到会话** | 差异化核心；批注数据形状须与现有消息/队列语义对齐，不破坏 pi 会话 |
| **P3 进阶（仅记方向）** | agent 自主浏览/验证、认证态会话共享、CSS/文本就地编辑回写、多标签与会话绑定 | 竞品也多处于演进中；本层**仅登记方向**，不进入当前版本范围 |

## 五、实现前必须做的探针（plan 之前，本 spec 不执行）

- **JCEF 多实例 / OSR 绘制**：新增一个浏览器 JBCefBrowser 到工具窗/编辑器，与现有面板共存时的绘制、焦点、生命周期（019 已知 OSR 帧滞后、GC 停顿坑）。
- **DevTools 可用性**：JCEF 下能否挂 DevTools / CDP，覆盖 DOM、Console、Network 到什么程度；若受限，替代方案（注入脚本采集 console/网络）。
- **元素选取与上下文采集**：注入脚本生成稳定选择器、读取计算样式与尺寸、裁剪截图在 OSR 下如何取；页面 CSP 对注入的影响。
- **批注覆盖层**：在不侵入被预览页面 DOM 语义的前提下绘制标注（独立 overlay / shadow DOM），与页面自身事件如何共存。
- **承载形态**：工具窗 Content 与编辑器 Editor 两种呈现各自的实现路径与切换语义；URL 地址栏在两种形态下的一致性。
- **安全**：URL 白名单/黑名单（本地优先、外部 URL 是否需要确认）、iframe/跨域、下载处理、是否隔离存储、与 037 系统浏览器策略的边界。**其中 HTTP / 不安全 HTTPS / 证书配置策略已由配套 spec [043 浏览器协议与证书策略](./../043-browser-protocol-cert/spec.md) 单独定义**（用户 2026-11-16 拍板仅覆盖内置浏览器 JCEF 面）；本探针的相关结论应回填 043。
- **会话注入数据形状**：批注作为文本消息还是结构化上下文（附件）进入 pi；大截图与 DOM 数据的体积/截断策略。

## 六、不做的事（本版本）

- 不实现、不拆 plan/tasks、不改任何源码——本次只记录方向。
- 不改 037：市场/外链默认仍走系统浏览器。
- 不做通用浏览器：不追求登录态、cookie profile、扩展、用户浏览器配置继承（竞品普遍回避）。
- 不在本 spec 承诺 P1–P3 的排期或技术方案；每层另立 spec 时再澄清与拍板。
- 不与 OAuth（014）混用——登录仍走系统浏览器；内置浏览器不承载认证流程。

## 七、与既有规格的关系

- **037**：外链白屏修复走系统浏览器，本能力独立并存，不冲突。
- **014**：OAuth 认证继续系统浏览器，内置浏览器明确不碰认证。
- **019**：多 Content / 多 JBCefBrowser 基建可复用，但实例计数与 token 分桶须隔离，防止污染 pi 会话（见 019 两条硬教训）。
- **041**：「UI → 会话/IDE」出口族兄弟——041 是代码块 → IDE，本能力是页面批注 → 会话；可共享「把 UI 上下文送进 pi」的通道设计，但不捆绑交付。

## 八、验证维度（仅列方向，实施 spec 再细化）

| 维度 | 关注点 |
|---|---|
| 基座 | 地址栏展示/编辑生效；前进后退刷新可用；localhost / file:// / 公开 URL 打开正确 |
| 形态 | 工具窗页签与编辑器呈现都能打开、切换不丢状态；不干扰 019 多实例 |
| 开发交互 | DevTools / 控制台日志可见、可复制进会话 |
| 批注 | 元素选取准确；批注附带的上下文完整；添加到会话后 pi 能据此修改且会话语义不坏 |
| 安全/边界 | 外链策略与 037 一致；认证页面不承载；隔离存储/白名单按探针结论落实 |

## 开放问题（留给后续实施 spec）

1. 「编辑框呈现」的精确形态：编辑器标签页（editor tab）内嵌预览，还是其它编辑区内嵌方式？两种呈现是否共享同一 URL 状态？
2. URL 策略：默认允许哪些协议/域名？外部 URL 是否需要用户确认？与系统浏览器的分工触发点如何呈现给用户？
3. DevTools 在 JCEF 下的可行形态与降级方案。
4. 批注回流是「纯文本 + 截图附件」还是「结构化上下文」——取决于 pi 当前消息/附件能力。
5. 会话与浏览器页签的生命周期绑定：会话切换时页签是否跟随、多个浏览器页签如何管理。
