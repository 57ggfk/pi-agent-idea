# Feature Specification: 连切会话不再堆积请求

**Feature Branch**: `release/0.5.8`

**Created**: 2026-11-12

**Status**: Implemented

**Input**: 用户报告（2026-11-12）
> 快速频繁切换会话，在上一个还没加载好的同时立即切换其他的可能会失败，出现会话切换失败的提示。

**难度定位**：小（改动集中在 `store.switchSession` 一个函数），但**取证难**——
本地连切 7 次只要 1.39s，怎么点都不失败；必须让 pi 变慢才会现形。

## 问题陈述

### 现象与实测

| 场景 | 结果 |
|---|---|
| 连点 3 个会话（间隔 400ms，每次都能点中） | 每次都在 ~250ms 内完成，**无重叠、无失败** |
| 同一次渲染周期内连点 7 个（搜索命中，见下） | 7 个 `switch.pending`，总 1390ms，**仍不失败** |
| 同上，但 pi 进程被挂起 4s | **`switch.failed 5012ms reason=timeout`**，踢回会话列表，`items=0` |

第三行就是用户看到的「切换会话失败」。前两行说明：**光点得快不够，必须同时有慢**。

### 根因

`switchSession` 每次点击都完整走一遍 `switch_session` RPC + 三个读。pi 按**到达顺序**
串行回答这些命令，于是 N 次点击 = N 个 `switch_session` 排在 pi 的管道里。
前端的预算是 `SWITCH_RPC_TIMEOUT_MS = 5s`（026 FR-001），而这个预算是**每个请求各自计时**的：

- 第 N 个请求真正的耗时 = 前面 N-1 个的总耗时 + 自己的耗时
- 一旦机器卡顿（IDE 停顿、CPU 争抢、大会话），这个累加轻易越过 5s
- 越界时前端判定「切换失败」→ 清 pending、跳回列表、给错误条
- 而 pi 其实很快会把最后一个目标切好——**用户看到的失败是假的**

021 D8 的 `switchSeq` 只保证「迟到结果不覆盖新结果」，它**不阻止把请求发出去**，所以队列照样堆积。

### 为什么「列表已经 disabled 了」挡不住

`SessionsView.tsx:207` 确实有 `disabled={switching}`（021 T309）。但：

1. **搜索结果跳转没有 disabled**：`session-hit-snippet` 按钮（`:158`）直接调 `openHit`，
   它不受 `pendingSwitch` 约束——这是能稳定复现的入口。
2. **disabled 生效依赖一次渲染**：React 重渲染有延迟，IDE 卡顿或合成事件连发时，
   第二下点击会落在「还是 enabled」的旧 DOM 上，照样进 `switchSession`。

## User Scenarios & Testing

### US1 - 狂点会话，最后停在最后点的那个 (P1)

用户手抖或着急，在会话列表/搜索结果里连点四五下。视图每次都立刻跳到最新点的那条，
底部不再弹出「切换会话失败」，等 pi 缓过来后直接显示最后那条的内容。

### US2 - pi 卡顿时连切，仍然落在最后点的那条 (P1)

机器卡顿（pi 一时无响应）期间连点。第一下之后的所有点击都不再给 pi 添负担；
pi 恢复后只处理「第一个」和「最后一个」，最后一个必然在预算内完成。

### US3 - 搜索结果跳转不跳到别的会话里 (P2)

在搜索结果里连点两条不同会话的命中。被取代的那次不再执行 `requestSearchJump`，
否则会把 A 的命中位置滚到 B 的会话里。

## Requirements

- **FR-001** 同一时刻 MUST 只有一个 `switch_session` 在飞；点击产生的「视图跳转」不受限制（仍每次都跳）。
- **FR-002** 在飞期间的新点击 MUST 只记录**最新目标**（覆盖式的单槽队列），不得逐个入队。
- **FR-003** 在飞的这次完成后，若有排队目标 MUST 立刻接力，且接力轮 MUST 重新读取当时的代际（`switchSeq`），
  不得沿用首轮的代际（否则接力结果会被自己的 seq 检查丢弃）。
- **FR-004** `switchSession` MUST 返回「这个 file 是否成了可见会话」的布尔值：
  被取代的点击返回 `false`，真正落地的返回 `true`。调用方据此决定是否需要事后操作 transcript。
- **FR-005** 被取代的点击 MUST NOT 挂起：排队者在你追我赶中被覆盖时要立刻 settle 为 `false`。
- **FR-006** `abort` 只在首轮执行一次（乐观 set 已把 `isStreaming` 置 false，后续轮次不该再 abort）。
- **FR-007** 模块级闸门（`switchBusy` / `switchQueued`）MUST 有显式重置入口 `resetSwitchGate()`，
  因为 store 的 `setState` 重置只清 state，不清闭包外的模块变量；测试间泄漏会让后续所有切换静默早退。

## 不做的事

- **不改 5s 预算**：026 FR-001 的判定没错，错的是让前面的请求白占预算。
- **不取消已在飞的 RPC**：pi 没有 cancel 命令，强行忽略只会让 pi 状态与前端不一致。
- **不给搜索结果按钮补 disabled**：合并之后连点已经无副作用，禁用反而让用户以为「卡住了」；
  视图照跳、点得越多越跟手，是更好的手感。

## 验证

| 层 | 用例 | 结果 |
|---|---|---|
| 单测 | 5 次重叠点击 → `switch_session` 调用次数 === 2，目标 `[a, e]`，返回值 `[false×4, true]` | 通过 |
| 单测 | 闸门空闲时不泄漏（连续两次独立切换都返回 true） | 通过 |
| 单测 | 迟到成功 / 迟到拒绝两条旧用例改写为「接力」语义 | 通过 |
| e2e | `sessions` + `scroll` + `jump-bottom` 21 条 | 通过 |
| 真机 | `probe-switch-race-hang.mjs`：pi 挂起 4.2s + 7 连点 | 修前 **FAIL 5012ms timeout**；修后 **PASS**，接力轮 242ms |
| 真机 | 同上，挂起 **8.2s**（超过 5s 预算） | 仍 **PASS**：超时的是被取代的那个，最后一个 3515ms 落地 |
