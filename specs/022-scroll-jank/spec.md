# 022 滚轮卡顿：长列表与下拉列表「滑到底再往上滑不动，停一下才行」

> 来源：用户 2026-11-10 反馈 ——「会话历史鼠标滚轮滑动到下方在往上滑不动，停一下才能滑动。选模型的下拉列表也有这个问题，好像光标悬浮在条目之外区域没有这个问题」，并补充「还有个性能问题」。
> 版本归属：**0.5.7**（该版本尚未发布，直接并入）
> 关联：011（模型选择器的 200 条上限与 `ensureVisible`）、018 US5（模型组折叠）、006（大纲/搜索跳转）、**021（会话切换延迟，同属」点下去没反应「一族）**
> **技术方案见 [plan.md](./plan.md)**（本文只写用户价值与可验收行为，不含技术选型）

## 需求拆解：三句话 → 三条 US

| # | 用户原话 | 现在的观感 | 本 spec 的处置 |
|---|---|---|---|
| 1 | 会话历史滚轮滑到下方，再往上滑不动，停一下才能滑动 | 滚到底之后向上滚，列表纹丝不动；鼠标停一下再滚才动 | US2（消息/会话列表滚轮跟手） |
| 2 | 选模型的下拉列表也有这个问题 | 同上，且**光标悬停在条目上时最明显** | US1（下拉列表：hover 不得抢滚轮） |
| 3 | 好像光标悬浮在条目之外区域没有这个问题 | 指到列表的空白处滚就正常 | 这句是**定位关键**：问题由「指针压在条目上」触发 → 见「已证根因」 |
| 4 | （补充）还有个性能问题 | — | US3 + 开放问题 Q1（待用户指明具体场景后归位） |

## 已证根因（下拉列表，代码可证）

两个下拉（模型选择器、Manage 的 provider 选择器）写着同一套逻辑：

1. 鼠标进入某一行 → `onMouseEnter` → `setHighlight(该行)`。
2. `highlight` 一变 → 有一个 `useEffect([highlight, open])` 立刻 `ensureVisible(list, 该行)`：两次 `getBoundingClientRect()`（强制同步布局）+ 一次 `querySelectorAll` 全表扫描。
3. 同一笔状态变化还触发**整张列表重渲染**：模型选择器每渲染一次都要为每个分组对全表 `visibleFlat` 做一次 `filter`，实测目录 359 条 → 每次 hover 重建 359 个 React 元素。

滚轮一动，指针下方的行就换，`mouseenter` 就再发一次 → **每滚一格触发一次全列表重渲染 + 一次强制布局**。主线程被这些活占满，滚轮事件排队，于是表现为「滑不动」；指针停住不再产生 `mouseenter`，主线程空出来，队列里的滚轮才一次性生效 —— 这正是用户观察到的「停一下才能滑动」和「指针在条目之外就正常」。

同一现象也解释了为什么**只有长列表明显**：条目越多，单次 hover 的重渲染与布局成本越高。

## 待证根因（会话消息列表）

消息列表没有 hover 状态，所以问题不在同一处。代码里有两个可疑点，需要真机量化后才能定权重：

| # | 候选 | 性质 |
|---|---|---|
| M1 | 「吸底」判定用的是**距离阈值**：`scrollHeight - scrollTop - clientHeight < 60` 就算贴底，贴底时任何一次消息更新都会把 `scrollTop` 拉回底部 | **代码可证的缺陷**：单次滚轮位移与 60px 同量级时，向上滚一格仍被判为「贴底」，于是被下一次更新拽回去；流式输出期间尤其明显 |
| M2 | 长列表在 JCEF（OSR）下的每帧光栅化成本：消息越多、代码高亮越多，滚动时主线程越忙，滚轮排队的概率越高 | 需真机取证（与 021 的 OSR 帧滞后同源） |

M1 无论 M2 是否成立都该修（它是一个明确的判定错误），M2 先用埋点量化再决定是否动渲染策略。

## User Stories

### US1 下拉列表：hover 不得抢滚轮

1. 指针压在某个条目上时，滚轮上下都能连续滚动，**不出现「停一下才动」**。
2. 鼠标悬停只改变**视觉**高亮，**不改变**「键盘当前项」：悬停第 5 行后，`↑/↓` 仍从原键盘项继续走，视觉高亮跟随悬停（由样式完成），两者不互相踩。
3. 悬停后直接按 Enter：选中**鼠标所指的那一项**（符合直觉），而不是键盘旧项。
4. 鼠标点击与 Enter 选中的是同一份数据（同一个索引空间），不出现「点 A 选到 B」。
5. 折叠分组、搜索过滤、当前项定位这三条既有行为不变（018 US5 / 011 US1 的验收不能被破坏）。

### US2 消息与会话列表：滚轮跟手，到底能立刻往回滚

1. 一直滚到最底部后，**向上滚一次就要立刻向上**，不需要停顿、不需要先动一下鼠标。
2. 判断「用户是否想留在底部」以**方向**为准：只要用户主动向上滚过，就不再用任何距离阈值判定把他重新吸附到底部。
3. 用户停在底部时，新消息到达仍然自动跟随（这是既有体验，不能因为修 bug 丢掉）；用户向上滚离底部后，新消息到达**不得**把视图拽回底部。
4. 会话列表（历史会话页）与消息列表行为一致：滚到底能立刻回滚。
5. 流式输出期间同样成立：向上滚即脱离吸附，并保持脱离。

### US3 长列表的每次交互成本有上限

- 与滚动/悬停无关的状态变化（如统计、队列、语言、主题）不得导致整屏消息重渲染。
- 悬停、滚动这类高频交互不得触发 React 状态更新（这是 US1 第 2 条的实现前提）。
- 视口之外的大块内容不参与每帧绘制（具体手段见 plan，属实现选择）。
- 上述三条都以**可断言的计数或耗时**验收，不靠手感。

### US4 卡顿可度量

- 两个指标必须先能取到数，才谈得上「修好了」：① 一次滚轮事件到列表实际位移的耗时；② 一次悬停触发了几次重渲染。
- 真机取值记录进执行记录，作为下次回归基线。

## 非目标

- 不引第三方虚拟列表库、不改消息 DOM 结构（`data-item-id`、`flash-target`、大纲/搜索的定位契约保持不变）。
- 不改模型选择器的 200 条上限与分组折叠（020 在改这块，本文只动 hover 语义；两者同在 0.5.7，实现时按 020 先落地、022 后叠加的顺序避免冲突）。
- 不做滚动位置持久化（切走再回来回到原位）。
- 不改消息列表的自动滚动动效；不引入「回到底部」悬浮按钮。
- 不优化首屏加载与模型目录体积（那是 020 与 017 的范围）。

## 验收口径（用户可感知 + 可断言）

| 场景 | 期望 | 断言方式 |
|---|---|---|
| 模型下拉：悬停第 5 行 | 第 5 行视觉高亮；键盘当前项**不变**（`data-active` 仍在原行） | e2e 断言 `data-active` 不变，与 `:hover` 视觉分离 |
| 模型下拉：悬停后按 Enter | 选中第 5 行 | e2e 断言选中项 = 悬停项 |
| 模型下拉：连续 20 次滚轮 | 列表位移单调，无回弹；不出现「不动」的间隙 | e2e 逐次断言 `scrollTop` 变化 |
| 消息列表：滚到底再向上滚一次 | `scrollTop` 立即减少，无需停顿 | e2e 断言一次 wheel 后 `scrollTop` 减少 > 0（100ms 内） |
| 消息列表：滚离底部后收到新消息 | 视图停在原处，不被拽回底部 | e2e/mock 推送一条消息后断言 `scrollTop` 不变 |
| 消息列表：停在底部时收到新消息 | 仍然自动跟随到底 | e2e 断言 `scrollTop` 等于最大滚动量 |
| 悬停/滚动任意列表 | 不产生 React 状态更新 | 单测（纯函数）+ 真机 perf 记录：hover 触发的重渲染次数 = 0 |
| 滚轮单次响应 | 真机取值为基线并记录（阈值见 plan） | `idea.log` 中的 perf 行 |

## 关于「还有个性能问题」

用户 2026-11-10 只说「还有个性能问题」，没有指明场景。默认按 **US3/US4 的量化**推进（这两条本身就是性能工作），具体场景等用户补充后归位：

- 如果指的是**切换/新建会话慢** → 已在 021，不重复立项。
- 如果指的是**首屏或长会话打开慢** → 并入 US3 的测量，若实测证明需要虚拟滚动，按 021 的拆分判据另立。
- 如果是**流式输出时整体卡** → 与本 spec 的 M2 同源，直接在 US3 内处理。

## 开放问题

- **Q1**：那条「还有个性能问题」具体在哪个场景？（决定是并入 US3 还是另立规格）
- **Q2**：悬停高亮完全交给 CSS 后，是否需要保留「悬停 350ms 后才高亮」之类的延迟？（默认不要，立即高亮更像原生列表）
- **Q3**：消息列表是否允许引入 `content-visibility` 这类会影响 `scrollHeight` 估算的手段？（默认允许，但必须保证「跳转到第 N 条」与「吸底」的定位仍然准确）
