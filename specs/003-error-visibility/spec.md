# Feature Specification: 静默失败可见化

**Feature Branch**: `003-error-visibility`

**Created**: 2026-11-02

**Status**: Draft

**Input**: 用户需求：「还有哪些需要实现的功能」→ UI_ISSUES.md 梳理时遗留的第 2、3 条隐患：
`store.init()` 里多个请求失败被 `.catch(() => undefined)` 吞掉、`filesCache` 失败后写死空数组且永不失效。
定稿时的补充事实：项目里**已存在**「可见错误」的正确范式（`set_model` 失败会往消息流插 system 条目），
只是没有推广到初始化链路。

## 问题陈述

用户看到空列表时的三种可能，界面上完全无法区分：

1. 确实为空（项目里没有文件 / pi 没有注册命令）；
2. 加载中（还没回来）；
3. 加载失败（pi 未就绪、桥接报错、文件索引未建好）。

第 3 种目前只进 `console.warn`，用户看不到。结果就是「`/` 和 `@` 一直是空的」这类问题
必须靠开发者打开 DevTools 才能定位——而 JCEF 里连 DevTools 都要额外操作。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 分清「真的空」和「加载失败」 (Priority: P1)

用户输入 `@` 想引用文件，菜单弹出来显示「No matching files」。他不知道是项目里真没匹配文件，
还是文件列表压根没加载成功。

**Why this priority**: 这是所有静默失败的共同表象，解决了它，其余几条才有意义。

**Independent Test**: 在 mock 里让 `files.list` 失败一次 → 打开 `@` 菜单 → 显示「文件列表加载失败」+ 重试按钮，
而不是「No matching files」。

**Acceptance Scenarios**:

1. **Given** 文件列表加载失败，**When** 用户输入 `@`，**Then** 菜单显示「文件列表加载失败」与失败原因摘要，
   并带「重试」操作；不得显示成「没有匹配的文件」。
2. **Given** 文件列表已成功加载但确实无匹配，**When** 用户输入 `@xyz`，**Then** 显示「没有匹配的文件」（不带重试）。
3. **Given** 命令列表加载失败，**When** 用户输入 `/`，**Then** 显示「命令列表加载失败」+ 重试。
4. **Given** 某个数据源仍在加载中，**When** 用户打开对应菜单，**Then** 显示加载中状态，不与「为空」混淆。

---

### User Story 2 - 失败后能就地重试 (Priority: P1)

pi 进程刚启动时请求失败是常态（竞态）。用户现在只能重开工具窗口或按 F5 碰运气。

**Why this priority**: 与 US1 成对——指出了失败却不给恢复手段，体验仍然断裂。

**Independent Test**: 触发一次失败 → 点重试 → 请求成功 → 列表正常渲染，全程不离开当前界面。

**Acceptance Scenarios**:

1. **Given** 某数据源处于失败态，**When** 用户点「重试」，**Then** 立即重新发起请求，界面进入加载中，
   成功后清除错误态。
2. **Given** 用户连续点重试，**When** 上一次请求仍在进行，**Then** 不重复发起（in-flight 去重），按钮呈禁用态。
3. **Given** 重试仍失败，**When** 第二次失败返回，**Then** 保留错误态但**不弹窗骚扰**，只更新错误文案。
4. **Given** pi 进程从 `starting` 变为 `running`，**When** 状态变化事件到达，**Then** 自动补拉一次此前失败的数据源
   （用户无需手动点）。

---

### User Story 3 - 文件列表随项目变化更新 (Priority: P2)

用户在项目里新建了文件，回到插件输入 `@` 却找不到它，必须重开工具窗口。

**Why this priority**: 影响面小于前两条（有 workaround），但属于「说到做不到」的体验缺陷。

**Independent Test**: 新建文件 → 在插件内触发一次刷新（或菜单打开时自动判定过期）→ `@` 能列出新文件。

**Acceptance Scenarios**:

1. **Given** 文件列表已缓存，**When** 用户新建文件后再次打开 `@` 菜单，**Then** 新文件可被检索到
   （通过 TTL 过期或显式失效，二者之一必须成立）。
2. **Given** 用户在 IDE 中删除了文件，**When** 再次打开 `@`，**Then** 已删除文件不再出现。
3. **Given** 缓存尚未过期，**When** 用户手动点刷新，**Then** 强制重新拉取并更新缓存时间戳。

---

### User Story 4 - 一处集中的诊断视图 (Priority: P2)

用户遇到问题时想知道「插件现在到底哪里不正常」，而不是一条条去触发菜单看。

**Why this priority**: 面向排障，价值真实但不如前三条日常。

**Independent Test**: 打开诊断视图 → 看到所有数据源的状态（就绪/失败/未加载）与最近错误摘要。

**Acceptance Scenarios**:

1. **Given** 多个数据源失败，**When** 用户打开诊断视图，**Then** 每项显示状态、最近一次错误消息、可单独重试。
2. **Given** 全部正常，**When** 用户打开诊断视图，**Then** 显示「全部正常」，不制造焦虑。
3. **Given** 某数据源从未加载，**When** 查看诊断，**Then** 标为「未加载」而不是「失败」。

---

### Edge Cases

- **pi 进程尚未就绪时的请求全部失败**：不得把这一批失败当成永久故障——pi 变 `running` 后要自动恢复。
- **桥接整体不可用（token 失效 / 服务未起）**：这是致命态，需要一条明确的全局提示，
  区别于单个数据源失败。
- **退出重连后错误态残留**：进程重启成功应清空过期的错误态，不得让用户看到早已解决的红点。
- **错误信息过长**：摘要截断，完整内容可在诊断视图展开；不得把整段堆栈塞进菜单。
- **mock 环境下大量方法故意不支持**：mock 缺失方法不应被当成「真实失败」污染诊断视图
  （用 `unsupported` 与 `failed` 区分）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个异步数据源 MUST 有明确状态：`idle` / `loading` / `ready` / `failed` / `unsupported`。
- **FR-002**: 界面 MUST 能区分「为空」与「失败」——两者的空态文案与可用操作不同。
- **FR-003**: 失败态 MUST 展示可读的错误摘要，并支持就地重试。
- **FR-004**: 重试 MUST 做 in-flight 去重，避免并发风暴。
- **FR-005**: pi 进程进入 `running` 时 MUST 自动补拉此前失败的数据源。
- **FR-006**: 文件与命令列表 MUST 具备失效机制（TTL 或显式失效），新建/删除文件后能反映。
- **FR-007**: 系统 MUST 提供集中诊断视图，列出各数据源状态、最近错误、单独重试入口。
- **FR-008**: 桥接整体不可用时 MUST 有区别于单源失败的全局提示。
- **FR-009**: mock 不实现的方法 MUST 记为 `unsupported`，不计入失败统计。
- **FR-010**: 所有错误态在对应问题消失后 MUST 能被清除，不得残留。
- **FR-011**: 错误摘要 MUST 截断展示（建议 ≤ 200 字符），完整内容仅在诊断视图展开。

### Key Entities

- **数据源**：标识（files / commands / models / thinkingLevels / policy / prefs / sessions / stats）、
  状态、最近错误、最后成功时间、重试计数。
- **诊断条目**：数据源标识、状态、错误摘要、完整错误、重试入口。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户遇到「列表是空的」时，能**仅凭界面**判断是空还是失败——不再需要 DevTools。
- **SC-002**: 从「发现列表空」到「恢复可用」的操作步数 ≤ 1 步（点重试），且不需要重开工具窗口。
- **SC-003**: pi 冷启动竞态导致的失败，100% 在进程就绪后自动恢复，无需用户干预。
- **SC-004**: 新建文件后，用户在不重开窗口的情况下能在 `@` 列表中检索到它。
- **SC-005**: 诊断视图中不存在「显示了失败但实际已恢复」的残留条目。

## Assumptions

- 现有 `set_model` 失败插入 system 消息的做法是「可见错误」的正确范式，本规格把它抽象成通用数据源状态机。
- 不引入全局通知系统（IDE 通知只用于致命态），普通加载失败一律就地呈现，避免骚扰。
- 文件列表的失效以 TTL 为主、显式失效为辅；TTL 具体值在 plan 里定。
- 本规格不改动桥接协议本身，只改前端状态管理；后端已有的 `FILES_TTL_MS` 缓存保留。
