# 0.5.7 真机复验：滚轮「往上滑不动」的第二根因（2026-11-11 晚）

用户装 0.5.7 后复测，报「滚轮滑到下方再往上滑不动，停一下才能滑动」，并说明三个列表都出现过、当时 pi 已空闲。**022 的 US2 没有真正解决这条**，但根因与 022 原文的 M1（60px 距离阈值）不同。

## 取证过程

| 步骤 | 结果 |
|---|---|
| 已装包是否含 022/021 代码 | 含（jar 内 `scroll.frame` / `switch.pending` 都在，前端 hash `index-Cq5qJe6z.js`） |
| `idea.log` 的 `[pi-agent] perf` 记录 | 只有 `switch.*`，**零条 `scroll.frame`** → 滚动期间没有掉帧，不是 M2（光栅化性能） |
| 空闲时应用层是否动过 `scrollTop` | 没有：`items` 是稳定的 store slice，吸底 effect 只在内容变化时跑；会话列表与模型下拉根本没有滚动代码 |
| Chromium 里复现 | 既有 e2e（含「流式中上滑不被拽回」新增用例）全绿 → 不是纯 JS 逻辑 |
| 对照实验：`.item-body` 的 `content-visibility` | **复现，且量级惊人** |

## 根因（已确证）

022 的 T410 给 `.item-body` 加了 `content-visibility: auto; contain-intrinsic-size: auto 120px`。会话刚加载时视口上方的消息从未渲染过，按 120px 提示高度占位，而真实消息高度是它的 3–6 倍（工具卡片、代码块）。向上滚一格，这些消息开始渲染、高度暴涨，**滚动锚定**为保持画面稳定把 `scrollTop` 往回推：

```
40 条高条目（真实高 26220px，占位后只有 5268px）
  有 content-visibility：10 格上滑（应上移 1200px）→ 实际向下移动 3234px
  无 content-visibility：10 格上滑 → 精确上移 1200px
```

停止滚轮、让布局稳定后才能正常滑，正是用户说的「滑不动，停一下才能滑动」。这条与 022 US2 直接冲突：US2 要修的就是这个症状，而 T410 又把它做回来了。

## 处置

- `.item-body` 改回 `content-visibility: visible`，并在 CSS 里写明两次失败（paint containment 裁工具条 + 本次的滚动锚定）与实测数字，避免以后再加回来。
- 保留 022 的另一半收益：`React.memo` + `sameActionIds`（重绘节省来自这里，与几何无关）。
- 回归守卫：`e2e/scroll.spec.ts` 新增 `the transcript body is not optimized with content-visibility`。
- 复用 T410 的撤销记录写进 `specs/022-scroll-jank/tasks.md`；`MANUAL_TEST.md` 的 022 段改为「长会话一次滚到底再往上滚，第一格就要向上走」。

## 仍未解释的部分

用户回答「三个列表都有」，但会话列表与模型下拉**没有** `content-visibility`，也不存在会话列表的滚动代码；空闲时应用层不写 `scrollTop`，且日志无掉帧。这两处若是同一个平台层问题，需要 JCEF 侧取证（`-Dide.browser.jcef.debug.port` + CDP attach）才能定量，下一步按用户复测结果决定是否上真机 CDP。

## 正向结果（当前构建）：**12/12 绿**

每条都是真滚轮事件（CDP `Input.dispatchMouseEvent` type=mouseWheel，一格 120px），10 格 = 应上移 1200px。

| 容器 | 10 格快速上滑 | 逐格 |

`.item-body` 实测 `content-visibility: visible`、`contain-intrinsic-size: none`。

**用户报的「三个列表都滑不动」在修复后不复现**：三个容器都是每格精确 120px，没有「停一下才能滑」。

## RED 对照：同一条会话，唯一变量是那条声明

运行时插 `<style>` 复现不出来——`contain-intrinsic-size: auto` 会**记住元素已经渲染过的尺寸**，后插入的声明拿不到「从未渲染」的状态（第一次注入实测 scrollHeight 反而从 10221 涨到 12871，就是这个原因）。必须让声明**在文档加载前**就存在，走 CDP `Page.addScriptToEvaluateOnNewDocument` + reload。

| 条件 | scrollHeight | 10 格上滑 | 结论 |
|---|---|---|---|
| `content-visibility: visible`（当前构建） | **10221** | **-1200** | 正确 |
| `content-visibility: auto; contain-intrinsic-size: auto 120px` | **14868**（+45%） | **-2105**（+75%） | 几何错乱 |

同一条会话、同一批消息，列表总高差 45%、同一手势的位移差 75%。**滚动位置与内容脱钩这件事在真机上被直接量到了**。

补充一个诚实的差异：合成页面里（首次加载、40 条构造的高条目）表现为**反向移动 3234px**，真机上表现为**超额移动 -2105px**。方向不同，成因同一——占位高度与真实高度不一致，滚动手势换算出的位移就不再对应内容。具体偏哪个方向取决于条目高度分布和此前的滚动历史，两种都是坏。

## 由此收敛的解释

- 三个列表都受影响：`content-visibility` 不是只作用在消息列表上——它让同一条会话多出 45% 的布局高度，整个渲染进程在滚动时持续重测量，任何容器的滚动都被拖住。这解释了「三个列表都有」而不必假设三个独立的 bug。
- `idea.log` 里零条 `scroll.frame` 不矛盾：那个埋点只量 wheel handler 内的**同步**耗时，测不到 handler 返回之后的重排。

  脚本一直等 `item > 40` 直到 90s 超时。改为按行文本里的「N 条消息」**自动挑最长会话**，等待条件放宽到 >10
  （43 条的会话只渲染约 25 个 item，工具结果不单独成项）。
- `probe-0.5.7-manual.mjs` 认领页面时补上 `[data-testid="tabs"]`，否则页面停在会话/管理页签时认不出来。
