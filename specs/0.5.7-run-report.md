# 0.5.7 真机复验：滚轮「往上滑不动」的第二根因（2026-11-11 晚）

用户装 0.5.7 后复测，报「滚轮滑到下方再往上滑不动，停一下才能滑动」，并说明三个列表都出现过、当时 pi 已空闲。**022 的 US2 没有真正解决这条**，但根因与 022 原文的 M1（60px 距离阈值）不同。

## 取证过程

| 步骤 | 结果 |
|---|---|
| 已装包是否含 022/021 代码 | 含（jar 内 `scroll.frame` / `switch.pending` 都在，前端 hash `index-Cq5qJe6z.js`） |
| `idea.log` 的 `[pi-agent] perf` 记录 | 只有 `switch.*`，**零条 `scroll.frame`** → 滚动期间没有掉帧，不是 M2（光栅化性能） |
| 空闲时应用层是否动过 `scrollTop` | 没有：`items` 是稳定的 store slice，吸底 effect 只在内容变化时跑；会话列表与模型下拉根本没有滚动代码 |
| Chromium 里复现 | 既有 e2e（含「流式中上滑不被拽回」新增用例）全绿 → 不是纯 JS 逻辑 |
| 对照实验：`.item-body` 的 `content-visibility` | **复现，且量级惊人** |

## 根因（已确证）

022 的 T410 给 `.item-body` 加了 `content-visibility: auto; contain-intrinsic-size: auto 120px`。会话刚加载时视口上方的消息从未渲染过，按 120px 提示高度占位，而真实消息高度是它的 3–6 倍（工具卡片、代码块）。向上滚一格，这些消息开始渲染、高度暴涨，**滚动锚定**为保持画面稳定把 `scrollTop` 往回推：

```
40 条高条目（真实高 26220px，占位后只有 5268px）
  有 content-visibility：10 格上滑（应上移 1200px）→ 实际向下移动 3234px
  无 content-visibility：10 格上滑 → 精确上移 1200px
```

停止滚轮、让布局稳定后才能正常滑，正是用户说的「滑不动，停一下才能滑动」。这条与 022 US2 直接冲突：US2 要修的就是这个症状，而 T410 又把它做回来了。

## 处置

- `.item-body` 改回 `content-visibility: visible`，并在 CSS 里写明两次失败（paint containment 裁工具条 + 本次的滚动锚定）与实测数字，避免以后再加回来。
- 保留 022 的另一半收益：`React.memo` + `sameActionIds`（重绘节省来自这里，与几何无关）。
- 回归守卫：`e2e/scroll.spec.ts` 新增 `the transcript body is not optimized with content-visibility`。
- 复用 T410 的撤销记录写进 `specs/022-scroll-jank/tasks.md`；`MANUAL_TEST.md` 的 022 段改为「长会话一次滚到底再往上滚，第一格就要向上走」。

## 仍未解释的部分

用户回答「三个列表都有」，但会话列表与模型下拉**没有** `content-visibility`，也不存在会话列表的滚动代码；空闲时应用层不写 `scrollTop`，且日志无掉帧。这两处若是同一个平台层问题，需要 JCEF 侧取证（`-Dide.browser.jcef.debug.port` + CDP attach）才能定量，下一步按用户复测结果决定是否上真机 CDP。

## 正向结果（当前构建）：**12/12 绿**

每条都是真滚轮事件（CDP `Input.dispatchMouseEvent` type=mouseWheel，一格 120px），10 格 = 应上移 1200px。

| 容器 | 10 格快速上滑 | 逐格 |

`.item-body` 实测 `content-visibility: visible`、`contain-intrinsic-size: none`。

**用户报的「三个列表都滑不动」在修复后不复现**：三个容器都是每格精确 120px，没有「停一下才能滑」。

## RED 对照：同一条会话，唯一变量是那条声明

运行时插 `<style>` 复现不出来——`contain-intrinsic-size: auto` 会**记住元素已经渲染过的尺寸**，后插入的声明拿不到「从未渲染」的状态（第一次注入实测 scrollHeight 反而从 10221 涨到 12871，就是这个原因）。必须让声明**在文档加载前**就存在，走 CDP `Page.addScriptToEvaluateOnNewDocument` + reload。

| 条件 | scrollHeight | 10 格上滑 | 结论 |
|---|---|---|---|
| `content-visibility: visible`（当前构建） | **10221** | **-1200** | 正确 |
| `content-visibility: auto; contain-intrinsic-size: auto 120px` | **14868**（+45%） | **-2105**（+75%） | 几何错乱 |

同一条会话、同一批消息，列表总高差 45%、同一手势的位移差 75%。**滚动位置与内容脱钩这件事在真机上被直接量到了**。

补充一个诚实的差异：合成页面里（首次加载、40 条构造的高条目）表现为**反向移动 3234px**，真机上表现为**超额移动 -2105px**。方向不同，成因同一——占位高度与真实高度不一致，滚动手势换算出的位移就不再对应内容。具体偏哪个方向取决于条目高度分布和此前的滚动历史，两种都是坏。

## 由此收敛的解释

- 三个列表都受影响：`content-visibility` 不是只作用在消息列表上——它让同一条会话多出 45% 的布局高度，整个渲染进程在滚动时持续重测量，任何容器的滚动都被拖住。这解释了「三个列表都有」而不必假设三个独立的 bug。
- `idea.log` 里零条 `scroll.frame` 不矛盾：那个埋点只量 wheel handler 内的**同步**耗时，测不到 handler 返回之后的重排。

- `probe-scroll-jcef.mjs` 把会话行号写死成「第 4 行 = 131 条消息的会话」，用户增删会话后该行变成 43 条，
  脚本一直等 `item > 40` 直到 90s 超时。改为按行文本里的「N 条消息」**自动挑最长会话**，等待条件放宽到 >10
  （43 条的会话只渲染约 25 个 item，工具结果不单独成项）。
- `probe-0.5.7-manual.mjs` 认领页面时补上 `[data-testid="tabs"]`，否则页面停在会话/管理页签时认不出来。

## 仍在 0.5.8 待办

2. 纯手感项仍需人眼，自动断言替代不了：切换瞬间是否残留旧帧（2026-11-11 已目验通过，**无残留**）、

   悬停工具条不像原先设想的那样必须靠人眼——
   `elementFromPoint` 命中测试就能抓住裁切，已转成自动断言。

# 滚动手感的 30fps 天花板（2026-11-11 夜，人眼反馈后补测）

人眼反馈：切换**没有旧帧残留**（该条目已转勾）；但长会话向上翻**偶发「卡一下」**，不是每次都复现。
自动断言抓不到它，所以新写了 `web/probe-scroll-hitch.mjs`（只读，不发消息不 fork），把「卡一下」拆成三种可测的量：

| 量 | 测法 | 结果 |
|---|---|---|
| 渲染掉帧 | rAF 逐帧间隔 + `long-animation-frame` 归因 | 5 轮扫动（每轮 81 格、共 405 格）：`maxGap 35–47ms`，**无一次 ≥50ms**，LoAF 条目为空 |
| 输入到滚动的延迟 | 每个滚轮配一次 CDP 往返计时 | p50 13ms / p95 33–36ms / max 47ms |
| 真实系统滚轮 | `mouse_event` 走 IDE 输入链路，页面记 60 个 `scroll` 事件的时间戳 | 事件间隔 p50 **34ms** / p95 **35ms**，无 100ms 以上的空档 |

## 真正测到的东西：整个 webview 就只跑 30fps

```
显示器（AMD 780M）59Hz → webview rAF 逐帧间隔恒为 33ms（取值只有 33 / 34）
把消息列表 visibility:hidden → 仍 33ms
把消息列表 display:none     → 仍 33ms
把整个 body 清空成一行字     → 仍 33ms
把 IDE 切到前台、无遮挡      → 仍 33ms
```

四个对照全部 33ms，说明这不是「列表太重画不动」，而是 **JCEF OSR 的固定 30fps 提交节奏**。
两条环境事实叠在一起：

- `ide.browser.jcef.out-of-process.enabled=false`（`options/ide.general.xml:9`，USER 设的）——
  webview 与 IDE **同进程**，IDE 自己的 GC / EDT 忙起来会直接推迟 OSR 的绘制；
- OSR 的 30fps 上限意味着**每帧 33ms 的预算**，而一档滚轮是 120px 的整跳（不是平滑动画），
  所以「连续滚时内容每 33ms 跳一次」是这台机器的物理上限，任何列表侧优化都换不到 60fps 的手感。

## 结论与边界

1. **不是 022 的回归**：022 修的是「向上滚被往回顶」，那条已由 `probe-scroll-jcef.mjs` 固化
   （10 格 = -1200px 精确命中、逐格单调），本次复测仍是绿的。
2. **不是列表的活太重**：空 body 也只有 30fps，且滚轮期间没有 LoAF、没有 ≥50ms 掉帧。
3. **仍不能证伪「偶发卡一下」**：进程内 JCEF 下，IDE 侧的绘制停顿发生在渲染进程之外，
   上面三个量都看不见。要抓它得录屏幕像素序列（看画面是否冻结），属于另一套探针，这轮没做。
4. 因此「手感顺」这一条**保持未勾**，并在此写清原因；同条目的「滚动条长度不来回跳」已自动验：
   4 个来回 × 6 个采样点，`scrollHeight` 恒为 10379、滚动条比例恒为 0.0719。

后续若要真的改善手感，方向不在消息列表，而在**绘制节奏**（例如评估
`ide.browser.jcef.out-of-process.enabled=true` 能不能拿到 60fps，或接受 30fps 并把一档滚动量调小），
这属于产品级取舍，需要单开规格，不应塞进 022。

# 30fps 天花板的真实原因：它是可改的（2026-11-11 深夜 A/B 实测）

上一段的结论「JCEF OSR 固定 30fps、换不到 60fps」**是错的**。用户要求验证 `out-of-process` 假设，
结果在验证过程中找到真正的开关。三组对照，同一台机器、同一个 131 条消息的会话、同一份探针：

| # | 配置 | `jcef version:` | rAF 逐帧间隔 | 判定 |
|---|---|---|---|---|
| 0 | `out-of-process=false`（用户原配置，基线） | `144.0.15.1191`（local） | 33.24ms（33/34） | 30fps |
| 1 | `out-of-process=true` | `remote_144.0.15.3416` + 5×`cef_server.exe` | 33.33ms（只有 33） | **仍是 30fps** |
| 2 | `out-of-process=true` + `osr.framerate=60` | `remote_...` | 33.33ms（两次采样） | **仍是 30fps** |
| 3 | `out-of-process=false` + `osr.framerate=60` | `144.0.15.1191`（local） | **16.67ms（只有 17）**×3 次 | **60fps** |

## 结论

- **`out-of-process` 与帧率无关**，假设不成立；remote 变体（默认值）自己把帧率压在 30。
- 真正的开关是 registry 键 **`ide.browser.jcef.osr.framerate`（默认 30）**，
  在 `options/ide.general.xml` 的 `<component name="Registry">` 里加一行即可，**需重启 IDE**。
- 字节码链路（`plugins/jcef-plugin` 里的 `intellij.platform.ui.jcef.jar`）：
  `JBCefBrowser()` → `JBCefBrowserBuilder.createBuilder()` 读 `ide.browser.jcef.osr.framerate` →
  存 `myWindowlessFrameRate` → `JBCefBrowserBase` 写 `CefBrowserSettings.windowless_frame_rate`。
  我们插件用的正是无参 `JBCefBrowser()`（`PiAgentPanel.kt:327`），所以这个键管得到我们的面板。
- **只有 local（同进程）变体吃这个键**。想拿 60fps 就必须留着 `out-of-process=false`，
  代价是 IDE 的 GC/EDT 停顿仍会推迟 OSR 绘制。

## 效果（`probe-scroll-hitch.mjs`，同一会话同样 4 轮）

| 指标 | 30fps（基线） | 60fps |
|---|---|---|
| 每轮帧数 | 111–115 | **196–207** |
| `maxGap` | 35–36ms | **19–20ms** |
| `inputRt` p50 / p95 | 12–13 / 32–36ms | **10–11 / 18–27ms** |

CPU（16 核机器，`TotalProcessorTime` 采样）：滚动中约 **42% 单核**，空闲 **1.3% 单核**（2.7% 总算力）。
30fps 下滚动 CPU 没做 A/B，按帧数推算应当接近一半，但**未实测**。

## 两件顺带发现

1. **切会话会卡在「仍在切换」且没有取消入口**。60fps 那次冷启动轮里，脚本在 2 秒内
   连切三次会话（A→B→C），最后一次 `switch.pending` 之后**再没有 `switch.ready`**，
   页面停在「仍在切换，pi 比平时慢一些」超过 90 秒；期间 pi 侧实际**已经**把会话切好了
   （重载前端后立刻渲染出 131 条消息），所以是**前端切换状态没被清掉**，不是 pi 慢。
   没有超时、没有重试、没有取消按钮，只能重载 webview 或重开工具窗。
   建议单开规格：切换请求要带超时 + 可取消，响应丢失要能自愈。
2. `switch.pending` 之后缺 `switch.ready` 这个签名，就是上面那种卡死的可观测表现，
   下次排障先看 `idea.log` 里有没有配对的 `switch.ready`。
