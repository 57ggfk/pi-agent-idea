# Feature Specification: 会话导航与检索（用户消息目录 / 会话内搜索 / 全会话搜索）

**Feature Branch**: `release/0.5.2`（本版直接在版本分支上做，不单开 spec 分支）

**Created**: 2026-11-04

**Status**: Draft

**Input**: 用户需求三条：「会话用户快速跳转」「会话内容搜索」「全会话搜索」。经澄清：
快速跳转 = **目录锚点效果，用户消息作为目录**；会话内搜索 = **搜本会话内容，支持常用快捷键与 🔍 按钮唤起**；
全会话搜索未单独澄清，按 `Sessions` 页既有范围（**当前项目**）实现，见 Assumptions。

## 问题陈述

会话变长之后，工具窗里只有一条没有尽头的滚动条。用户想回到「十几轮之前那个我提问的地方」，
唯一手段是往上滚并肉眼找；想找「pi 当时是怎么解释那个异常的」，也只能滚。
`Sessions` 页的过滤框只匹配标题 / 预览 / 会话 id，**碰不到正文**，所以「我记得在哪次会话里说过」
这种最典型的检索需求完全没有入口。

| 需求 | 现状 |
|---|---|
| 跳到本会话的某次提问 | 手动向上滚动 + 肉眼找 |
| 在本会话里找一段文字 | 无（只能通读） |
| 在历史会话里找一段文字 | 只能按标题/预览过滤，正文不可搜 |
| 命中之后跳过去 | 不存在这个概念 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户消息目录（快速跳转）(Priority: P1)

用户在一个长会话里，想看自己都问过什么、并跳回其中某一条。Chat 顶部有一个目录入口，
展开后按时间顺序列出本会话的**全部用户消息**（单行截断），点击任意一条，消息列表滚动到该消息，
该消息短暂高亮约 2 秒，目录项同步标记为当前项。

**Why this priority**: 纯前端、零协议风险，且是三条需求里用户感知最强的一条（长会话第一痛点）。

**Independent Test**: 造 30 条用户消息 → 打开目录 → 断言条目数 = 用户消息数、顺序与正文一致 →
点第 3 条 → 断言该消息 rect 落在视口内且高亮类出现后消失。

**Acceptance Scenarios**:

1. **Given** 一个有 N 条用户消息的会话，**When** 打开目录，**Then** 列出 N 条、顺序与出现顺序一致，
   每条只显示一行文本（超出省略），首条为最早。
2. **Given** 目录已打开，**When** 点击第 k 条，**Then** 该消息滚动到消息区可见位置（顶部留 8–16px 偏移），
   出现约 2 秒的高亮，目录项标记为当前。
3. **Given** 目录已打开，**When** pi 流式输出结束后用户又发了一条，**Then** 新提问立刻出现在目录末尾
   （不需要关闭重开）。
4. **Given** 一个空会话（无用户消息），**When** 查看顶部工具条，**Then** 目录入口不出现（不显示点了没反应的按钮）。
5. **Given** 会话中有图片消息（无文本），**Then** 目录项显示占位文案（如「图片」），仍可跳转。
6. **Given** 目录面板展开，**When** 面板宽度处于 360px，**Then** 面板完整落在 `.app` 内，不出横向滚动。

### User Story 2 - 会话内搜索 (Priority: P1)

用户想在本会话里找一段文字。按 `Ctrl+F`（macOS `Cmd+F`）或点顶栏 🔍，输入关键词，
命中项在正文中高亮，浮层显示 `当前/总数`，`Enter` 跳到下一个、`Shift+Enter` 上一个，`Esc` 关闭并清除高亮。

**Why this priority**: 与 US1 同属「长会话定位」，但覆盖面更广（pi 的回复才是主要查找目标）。

**Independent Test**: 造含 3 处 `timeout` 的会话 → 唤起搜索 → 输入 `timeout` → 断言计数 `1/3` →
连按 Enter 两次数值到 `3/3` 且第 3 处滚动进视口 → Esc 后高亮归零。

**Acceptance Scenarios**:

1. **Given** Chat 页，**When** 按 `Ctrl+F` / `Cmd+F`，**Then** 搜索框出现并获得焦点，
   **不触发** IDE 自身的「在文件中查找」或 JCEF 内建查找栏。
2. **Given** 搜索框已打开，**When** 点 🔍 按钮，**Then** 行为与快捷键完全一致（同一组件、同一状态）。
3. **Given** 输入 `timeout` 命中 3 处，**Then** 计数显示 `1/3`，第一处滚动进视口并高亮，
   所有命中都有可见标记。
4. **Given** 命中 3 处，**When** 连按 Enter，**Then** 依次到 `2/3`、`3/3`、再回到 `1/3`（循环）。
5. **Given** 搜索词无命中，**Then** 显示 `0/0` 与「无匹配」文案，不显示红色报错。
6. **Given** 搜索打开，**When** 按 Esc，**Then** 搜索框关闭、所有高亮消失、滚动位置不变（不跳回顶部）。
7. **Given** 会话正在流式输出，**When** 搜索打开，**Then** 新到达的文本同样可被搜到（结果集随内容更新）。
8. **Given** JCEF 不支持 CSS Custom Highlight API，**Then** 高亮仍可见（走降级通路），
   且 markdown 结构（代码块、列表）不被破坏。

### User Story 3 - 全会话搜索 (Priority: P2)

用户记得「某次会话里 pi 讲过一段迁移步骤」，但不知道是哪次。在 Sessions 页搜索框输入关键词，
除标题/预览过滤外，同时扫描**本项目全部会话正文**，把命中的会话排在前面并显示命中片段
（关键词高亮，最多 2 条片段）。点结果 → 切到该会话，并定位到命中的那条消息、高亮 2 秒。

**Why this priority**: 价值高，但要新增后端扫描 + 片段生成 + 跨会话定位，成本高于 US1/US2，
排在其后；没有它也不影响前两条独立交付。

**Independent Test**: mock 两个会话文件，各含关键词一次 → Sessions 搜索 → 断言两个会话都命中、
片段含关键词 → 点第二个 → 断言切到该会话且目标消息在视口内。

**Acceptance Scenarios**:

1. **Given** 当前项目有会话 A（正文含 `uniq-token-abc`）与会话 B（不含），**When** 在 Sessions 搜索框
   输入 `uniq-token`，**Then** A 出现在结果中并显示命中片段，B 不出现在命中结果里（仍可按标题过滤规则保留）。
2. **Given** 关键词命中同一会话的 3 条消息，**Then** 该会话只出现一次，片段最多展示 2 条，
   并显示命中总数（如 `3 hits`）。
3. **Given** 命中结果已显示，**When** 点击其中一条片段，**Then** 切到该会话（Chat 页签激活），
   目标消息滚动进视口并高亮 2 秒。
4. **Given** 输入不足 2 个字符，**Then** 只做标题/预览过滤，不触发正文扫描（避免每次按键全盘扫描）。
5. **Given** 本项目有 200 个会话文件，**When** 搜索，**Then** 结果在 2 秒内出现；
   超时或触达扫描上限时显示「已扫描 X 个会话」提示，而不是静默返回空。
6. **Given** 搜索进行中用户又改了关键词，**Then** 只呈现最后一次输入的结果（旧请求作废，不闪回）。
7. **Given** 会话文件正在被 pi 写入（半行 JSONL），**Then** 搜索不崩溃，跳过无法解析的行。

### Edge Cases

- **正文含正则元字符**（`a.b`、`(`、`*`）：按字面量匹配，不得按正则解释。
- **大小写与全角**：英文不区分大小写；中文全角/半角标点不做归一化（按原文匹配），但输入两侧空格需 trim。
- **超长会话**（单个文件 > 20MB）：只扫前 N MB 并标记「已截断」，不把窗口卡死。
- **命中在 thinking 块**：默认不检索 thinking（未展开内容），也不检索 base64 图片数据。
- **工具输出**：命令卡片里的输出**可被检索**（用户经常靠命令输出定位），但命中在折叠状态时需自动展开该卡片。
- **目录/搜索与消息操作条共存**：两者都不得改变消息列表几何（`scrollWidth === clientWidth`）。
- **滚动条出现**：跳转后消息列宽度变化不得让居中列抖动（宪法 III）。
- **会话切换后**：目录与搜索结果必须重置，不得残留上一会话的条目。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Chat 顶部 MUST 提供用户消息目录入口；目录列出本会话全部 user 消息，顺序与出现顺序一致。
- **FR-002**: 点击目录项 MUST 把目标消息滚动到可见区（顶部偏移 8–16px），并高亮约 2 秒。
- **FR-003**: 目录 MUST 随新消息增量更新；空会话时入口 MUST 隐藏。
- **FR-004**: Chat MUST 支持 `Ctrl+F` / `Cmd+F` 唤起会话内搜索，且 MUST 阻止 IDE / JCEF 的默认查找行为。
- **FR-005**: 顶栏 🔍 按钮 MUST 与快捷键唤起同一搜索组件、共享同一状态。
- **FR-006**: 搜索 MUST 覆盖当前会话所有 `text` 块与工具输出；MUST NOT 检索 thinking 与图片数据。
- **FR-007**: 搜索 MUST 显示 `当前/总数` 计数，`Enter` / `Shift+Enter` 循环导航，`Esc` 关闭并清除高亮。
- **FR-008**: 命中 MUST 有可见高亮；高亮 MUST NOT 破坏 markdown 结构（代码块围栏、列表、表格）。
- **FR-009**: 搜索 MUST 在流式输出过程中对新到达文本生效（结果集可增量更新）。
- **FR-010**: Sessions 搜索框 MUST 在输入 ≥2 字符时同时触发本项目全会话正文扫描（防抖 ≤300ms）。
- **FR-011**: 全会话搜索 MUST 按会话聚合命中、给出含关键词的片段（每会话最多 2 条）与命中总数。
- **FR-012**: 点击全会话搜索结果 MUST 切换会话并把目标消息滚入视口、高亮 2 秒。
- **FR-013**: 全会话扫描 MUST 在后台线程执行（不得阻塞 EDT），MUST 有扫描上限与耗时上限，
  超限 MUST 有可见提示。
- **FR-014**: 搜索 MUST 按字面量匹配，不得把用户输入当正则；解析失败的行 MUST 被跳过而非抛出。
- **FR-015**: 会话切换 MUST 重置目录与两者的结果状态。
- **FR-016**: 所有新增面板 MUST 落在 `.app` 容器内，且不引起消息列表横向滚动或轴心偏移（宪法 II/III）。

### Key Entities

- **用户消息目录项**：`{itemId, 文本摘要（单行截断）, 时间序号}`，仅 user 角色。
- **会话内命中**：`{itemId, blockIndex, 字符偏移, 所在块类型(text/tool-output)}`。
- **全会话命中**：`{file, sessionName, hits[{role, snippet, entryIndex}], hitCount, modifiedAt}`。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 从「想看第 5 次提问」到「已在视口中」的操作为 2 步（打开目录 → 点击），
  e2e 可断言目标消息 rect 在视口内。
- **SC-002**: 本会话内定位一个关键词 ≤3 次按键（`Ctrl+F` → 输入 → Enter），计数显示正确。
- **SC-003**: 跨会话定位一条历史消息 ≤4 步（切 Sessions → 输入 → 点击结果），切会话后目标消息在视口内。
- **SC-004**: 200 个会话、20MB 总量下搜索 P95 ≤2s，UI 不冻结（e2e 期间连续点击页签仍响应）。
- **SC-005**: 既有几何断言套件（`web/e2e/layout-regressions.spec.ts`）全绿，新增面板加入 360/430/900 三档断言。

## Assumptions

- **全会话搜索范围为当前项目**：与 `Sessions` 列表同源（`PiSessionIndex.list(project.basePath)`），
  不跨项目、不搜其他工作区；跨项目检索需要新的索引层，明确不在本轮。
- **用户消息目录是浮层面板而非常驻侧栏**：工具窗最窄 360px，常驻侧栏会把消息列压到不可读。
- **搜索不引入第三方库**：中文按子串匹配（不做分词/模糊），英文大小写不敏感；模糊匹配与拼音首字母
  留作后续。
- **命中高亮依赖 CSS Custom Highlight API，降级用 DOM 包裹**：具体取舍在 plan 阶段定，
  验收只约束「高亮可见 + markdown 未被破坏」。
- **跨会话定位以「消息序号」为锚**：pi 的 RPC `get_messages` 只给正文，没有稳定 per-message id，
  因此定位用「第 k 条消息」对齐；若 pi 后续提供 id，再升级（plan 阶段记录）。
