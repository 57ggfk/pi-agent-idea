# Feature Specification: Manage 面板功能补全

**Feature Branch**: `001-manage-completeness`

**Created**: 2026-11-02

**Status**: Draft

**Input**: 用户需求：「还有哪些需要实现的功能」→ 盘点发现 Manage 面板对 pi 生态的管理能力停在一半：
能加不能停、能装不能升、能看不能改。本规格把四类「半截功能」补齐。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 临时停用某个 MCP 服务器 (Priority: P1)

用户装了若干 MCP 服务器，其中一个今天连不上、或者启动很慢拖慢每次对话。用户想**临时关掉它**，
过几天再打开。现在面板只能「删除」，删掉就得重新填一遍 command/args/env，配置直接丢失。

**Why this priority**: 这是唯一会造成**用户数据损失**的缺口——想停用只能删除。
其余三条是效率问题，这条是破坏性问题，所以排第一。

**Independent Test**: 在 Manage 面板选中任一 MCP 服务器 → 点停用 → 该项显示为已停用且会话启动不再加载它；
再点启用 → 状态恢复且配置一字未改。

**Acceptance Scenarios**:

1. **Given** 一个已配置且启用中的 MCP 服务器，**When** 用户点「停用」，**Then** 该服务器在列表中标为已停用，
   且新开的会话不再连接它；配置内容（命令、参数、环境变量）完整保留。
2. **Given** 一个已停用的 MCP 服务器，**When** 用户点「启用」，**Then** 状态恢复为启用，新会话重新连接，
   无需用户重新填写任何配置。
3. **Given** 用户停用了某服务器，**When** 关闭并重开 IDE，**Then** 停用状态仍然保持（不是内存态）。
4. **Given** 用户停用了一个正在当前会话中使用的 MCP 服务器，**When** 停用生效，**Then** 界面明确提示
   「需新会话生效」，不得让用户误以为当前会话已经断开。

---

### User Story 2 - 一键更新已安装的扩展包 (Priority: P2)

用户装的某个扩展包发了新版，修了他正遇到的问题。现在他只能先去终端 `pi install` 覆盖，
或者删掉再装——而在 IDE 里明明有「扩展包」页签。

**Why this priority**: 高频且低成本，但不像 US1 那样有数据损失风险，所以排第二。

**Independent Test**: 对一个有可用更新的扩展包点「更新」→ 更新进度可见 → 完成后列表中的版本号变化，
且失败时能看到原始错误输出。

**Acceptance Scenarios**:

1. **Given** 扩展包列表中有可更新的包，**When** 用户点「更新」，**Then** 执行更新并在完成后刷新列表版本号。
2. **Given** 更新过程中，**When** 用户观察界面，**Then** 有进行中状态（按钮禁用 / 转圈），
   不允许重复点击造成并发安装。
3. **Given** 更新失败（网络中断、源不可达），**When** 失败返回，**Then** 界面显示原始 stderr 摘录与退出码，
   并说明「已安装版本可能仍是旧版」，不得只显示「失败」。
4. **Given** 某个包没有可用更新，**When** 用户查看该行，**Then** 不显示更新按钮（不给无效操作）。

---

### User Story 3 - 检查并更新 pi 本体 (Priority: P3)

用户看到 pi 发了新版本，想升级。现在面板只显示「pi 1.4.0」，没有任何升级入口，
用户得自己去终端敲 npm 命令。

**Why this priority**: 有价值但可替代（终端能升），且涉及全局环境改动风险较高，排第三。

**Independent Test**: 环境区显示当前版本与更新入口 → 点更新 → 完成后版本号变化，
或明确告知「已是最新」，或给出原始错误。**不要求**插件主动联网判断有无新版本。

**Acceptance Scenarios**:

1. **Given** 已安装 pi，**When** 用户打开环境区，**Then** 显示当前版本 + 更新入口（不给「有新版本」这类未经确认的角标）。
2. **Given** 用户触发更新，**When** pi 正在运行会话，**Then** 先提示「更新会重启 pi 进程，进行中的会话将中断」，
   用户确认后才执行。
3. **Given** 更新成功，**When** 完成后，**Then** 界面版本号刷新，并在状态栏反映新版本；旧进程已被替换。
4. **Given** 已是最新版本，**When** 用户点更新，**Then** 明确显示「已是最新」，不得谎报已更新。
5. **Given** 更新失败或权限不足（如全局 npm 目录不可写），**When** 失败返回，**Then** 展示原始错误
   并给出可执行的修复建议（例如需要 sudo / 需要改 npm prefix）。

---

### User Story 4 - 查看并编辑自定义 Provider 配置 (Priority: P4)

用户想接一个自建/第三方模型服务，需要改 `models.json`。现在认证面板只把 provider 名字列出来，
既看不到配置详情，也没有入口跳到文件里改——用户得自己去 `~/.pi/agent/` 翻目录。

**Why this priority**: 受众窄（高级用户），但缺了会让「未使用过 pi 的用户零门槛配置」这条产品定位打折扣。

**Independent Test**: 认证面板中每个自定义 provider 有「查看配置」入口 → 打开后能看到该 provider 的配置项
（密钥类字段掩码）→ 有「在编辑器中打开」按钮能直接打开对应文件。

**Acceptance Scenarios**:

1. **Given** `models.json` 中有自定义 provider，**When** 用户点该 provider，**Then** 展示其 provider 类型、
   base URL、模型列表等非敏感字段，密钥类字段只显示是否已配置（不回显值）。
2. **Given** 用户点「在编辑器中打开」，**When** 文件存在，**Then** 在 IDE 编辑器中打开 `models.json` 并定位到该 provider 段。
3. **Given** `models.json` 不存在或格式损坏，**When** 用户查看认证面板，**Then** 显示明确原因
   （未配置 / 无法解析，附错误位置），不得让整个面板空掉或静默失败。

---

### Edge Cases

- **pi 版本过老，不支持某个子命令**：必须显式降级——隐藏该操作或标注「需要 pi ≥ x.y」，不得点击后无反应。
- **MCP 服务器配置在项目级（`.pi/mcp.json`）而非用户级**：停用状态写入哪一层必须与配置所在层一致，
  不得出现「用户级停用了但项目级仍生效」。
- **更新过程中 pi 进程被用户手动杀掉**：界面要能回到可重试状态，不能永久停在「更新中」。
- **离线环境**：检查更新失败不等于「已是最新」，两者必须区分显示。
- **同时打开两个 IDE 窗口**：一处的停用/更新，另一处刷新后应看到一致状态。
- **磁盘只读或 `~/.pi/agent/` 权限不足**：所有写操作失败都要给出可执行的修复建议，而不是抛栈。

## Requirements *(mandatory)*

### Functional Requirements

**MCP 启停**

- **FR-001**: 用户 MUST 能在 MCP 列表中停用/启用任一服务器，且不丢失其配置。
- **FR-002**: 停用状态 MUST 持久化到配置所在层级（用户级或项目级），IDE 重启后保持。
- **FR-003**: 系统 MUST 明确区分「停止运行」与「删除配置」两种语义，删除仍需二次确认，停用不需要。
- **FR-004**: 若被停用的服务器正被当前会话使用，系统 MUST 提示需新会话生效。

**扩展包更新**

- **FR-005**: 用户 MUST 能对已安装的扩展包触发更新，且能看到进行中状态。
- **FR-006**: 系统 MUST 在更新完成后刷新版本信息；没有可用更新时不展示更新入口。
- **FR-007**: 更新失败时 MUST 呈现原始错误输出与退出码，并说明当前安装状态可能未变。

**pi 本体更新**

- **FR-008**: 环境区 MUST 显示当前版本，并提供更新入口；更新结果（已最新 / 已更新到 x.y.z / 失败）
  MUST 来自 pi 的实际输出，不得由插件自行猜测。
- **FR-009**: 已是最新时 MUST 明确告知，不得显示「更新成功」。
- **FR-010**: 触发更新前，若存在运行中的会话，MUST 先告知会影响运行中的任务并取得确认。

**Provider 配置**

- **FR-011**: 认证面板 MUST 展示自定义 provider 的非敏感配置项，密钥类字段只显示「已配置/未配置」。
- **FR-012**: 用户 MUST 能一键在 IDE 编辑器中打开 `models.json`。
- **FR-013**: 文件缺失或损坏时 MUST 显示具体原因，不得静默空白。

**通用**

- **FR-014**: 所有写操作 MUST 遵循宪法第 IV 条：写前备份、结构化文件写前校验、失败原样呈现错误。
- **FR-015**: 所有新增操作 MUST 在 pi 不支持时显式降级，并说明所需最低版本。

### Key Entities

- **MCP 服务器**：名称、传输方式（stdio/HTTP）、命令与参数或 URL、来源层级（用户级/项目级）、启用状态、连接状态。
- **扩展包**：标识（npm 名 / git 地址 / 本地路径）、已安装版本、可用版本、安装层级。
- **pi 运行时**：可执行文件路径、当前版本、可用版本、是否运行中。
- **自定义 Provider**：名称、类型、base URL、模型清单、凭据是否就绪（不含凭据值）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户停用一个 MCP 服务器后重新启用，配置零丢失——不需要重新输入任何字段。
- **SC-002**: 完成「停用一个 MCP 服务器」的操作步数从目前的「删除 + 重新添加（约 8 步、需回忆原配置）」
  降到 2 步以内（点击 + 确认生效）。
- **SC-003**: 扩展包从「发现新版本」到「更新完成」全程不需要离开 IDE。
- **SC-004**: 所有更新/停用操作的失败场景，用户都能在界面上直接看到原始错误文本，
  无需去 IDE 日志里翻（目标：100% 的失败路径有可见错误）。
- **SC-005**: 自定义 provider 从「想改配置」到「编辑器里打开对应文件」不超过 2 次点击。

## Assumptions

- **已实测**：pi 1.4.0 的 `mcp` 子命令只有 `add / remove / list / login / logout`，**没有** enable/disable。
  因此「停用」按配置层实现（条目移出 `mcp.json` 并存入插件侧停用仓库，启用时回填），
  对 pi 而言等价于该服务器不存在。
- **已实测**：pi 原生提供 `pi update [source|self|pi] [--self|--extensions|--models|--all] [--extension <source>]`，
  扩展包更新与本体更新都复用它，插件不自行拼装包管理器命令，也不自建分发。
- 由于不存在 check-update 子命令，规格**不要求**插件主动判断「有无新版本」，只要求触发后如实转述结果。
- 扩展包更新沿用 `pi update` 的单包形式，不引入新的分发渠道。
- 自定义 provider 编辑只做「打开文件」，不在插件内做表单式编辑（避免与 pi 的 schema 演进耦合）。
- 本规格不改变任何现有默认值，因此不涉及跨版本迁移。
