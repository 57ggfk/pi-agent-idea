# 021 会话切换与新建：点击后 1s+ 才有反应

> 来源：用户 2026-11-10 反馈两条 ——「新建会话，等 1s 多才进入新会话」「历史会话，点击等 1s 多才进入到会话」。
> 版本归属：**0.5.7**（该版本尚未发布，直接并入）
> 关联：007（Fork / 新建确认框）、005（队列确认）、006（会话目录 / 大纲 / 搜索在切换时重置）、011（会话列表只读模型）、012 T121、**0.5.4 的 JCEF 帧滞后修复**（`ide.repaint`）
> **技术方案见 [plan.md](./plan.md)**（本文只写用户价值与可验收行为，不含技术选型）

## 需求拆解：两句话 → 五个 User Story

| # | 用户原话 | 现在的观感 | 本 spec 的处置 |
|---|---|---|---|
| 1 | 新建会话，等 1s 多才进入新会话 | 点「新建」→ 旧对话原样停在屏幕上 → 约 1s 后突然清空 | US1（立即反馈）+ US2（旧对话立即让位）+ US4（后台重扫不再拖累） |
| 2 | 历史会话，点击等 1s 多才进入到会话 | 点会话行 → 列表页不动 → 约 1s 后跳到对话页，且先是一片空白 → 内容再浮现 | US1 + US3（立即进入目标会话）+ US4 |
| — | （隐含要求） | 现在没有可被验证的延迟标准，改完也不知道算不算解决 | US5（埋点 + 阈值 + 回归用例） |

## 现象：用户经历的四个阶段

这两条不是「一个 RPC 慢」，而是**同一条链路上四段等待串起来**，所以体感是 1s 多而不是几百毫秒。每一段都有代码上的确定性解释（精确定位见 plan）：

| 阶段 | 用户看到什么 | 成因（代码事实） |
|---|---|---|
| ① 点了没反应 | 按钮/会话行看不出任何变化，没有转圈、没有禁用、没有文案 | 两处动作都是「先 `await` RPC，再改界面」；RPC 回来之前 store 一个字都不写 |
| ② 界面没动 | 新建时旧对话照旧；切换时列表页照旧 | 历史切换只有等 RPC 成功后才 `set({tab:"chat"})`；新建甚至根本不换 view，只是清 `items` |
| ③ 换了但是空的 | 跳到对话页，一条消息都没有 | 切换路径在跳转的同一笔 `set` 里把 `items` 清空，内容要等下一轮 `get_messages` 才回来；这一轮是**串行**的第四段等待 |
| ④ 旧帧还挂着 | 明明已经切页，屏幕上仍残留上一屏 | 0.5.4 真机已证实的 **JCEF OSR 帧滞后**：修复（`ide.repaint`）只接在顶层页签与 Manage 子页签的点击上，**会话切换与新建是 store 内部改 view，从不触发重绘** |

补充事实（决定了修复不能只做前端）：会话列表读取在 Kotlin 侧是**全量扫描**——遍历整个 `~/.pi/agent/sessions` 树、逐文件按行解析（每个文件最多解析 4000 行 JSON），再按 cwd 过滤出本项目。本机实测 **70 个会话文件 / 4.8MB / 14 个项目目录**，且这个成本随「所有项目的历史总量」线性增长，而不是随当前项目增长。它被 `new_session`、进入会话页、重命名、删除等动作反复触发。

## User Stories

### US1 点击后立刻有反馈

- 点击「新建」或某个会话行之后 **150ms 内**，界面必须出现可见变化：目标视图已经切过去（或空态/骨架已出现），并且有一处明确的「正在切换」提示。
- 切换进行中，界面不得表现得像点击被丢弃：不能出现「点了没反应、再点一次」的重复点击。
- 重复点击以**最后一次**为准，先前那次的结果不得覆盖后来的目标。

### US2 新建会话：旧对话立即让位

- 确认新建后，旧对话**立即**从主区域消失，显示新会话的空态；不等待 pi 确认。
- 若 pi 侧新建失败，旧对话必须**原样恢复**并给出错误提示，不得出现「对话被清空且找不回」。
- pi 确认之前，输入框可以显示（保留草稿/引用 chip），但发送必须处于不可用状态并说明原因；确认后自动恢复可用。
- 新建完成后，会话列表的重扫在后台进行，不阻塞空态出现、也不阻塞用户可以开始输入。

### US3 历史会话：立即进入目标会话

- 点击会话行后**立即**跳到对话页，不再停留在列表页等 RPC。
- 内容尚未就绪的这段时间显示占位（骨架/「正在载入会话…」），不得显示成「这个会话是空的」。
- 内容到达后一次性替换占位，不允许把上一个会话的消息残留在列表里（旧内容必须在跳转的同一笔状态更新里清掉）。
- 若切换失败，回到会话列表并提示失败原因，不留在空白会话里。
- 正在流式输出时切换：仍然先中断旧会话（沿用既有语义），但**中断过程不阻塞界面跳转**。

### US4 会话列表读取不再随历史总量变慢

- 进入会话页、新建会话后的列表刷新，速度不随「所有项目的会话总量」明显劣化；同一项目下新增会话不必付出「重扫全部项目」的代价。
- 列表内容与 `sessions.list` 的既有语义保持一致：最近修改优先、最多 100 条、字段（名称/预览/条数/时间）不变。
- 列表刷新不得与切换动作争抢，导致切换变慢。

### US5 延迟可度量、可回归

- 四个关键时点各自埋一个可读取的耗时记录（点击 → 界面有变化 → 内容就绪 → 可再次发送），能按需在 IDE 日志里取到。
- 关键阈值以 e2e 断言固定下来：用可注入的**人为延迟**模拟慢 RPC，断言界面仍在阈值内反馈（不靠真机手感，也不因机器快慢而抖动）。
- 真机取值记录进执行记录，作为下一次回归的基线。

## 非目标

- **不改 pi 进程自身的 `new_session` / `switch_session` 耗时**（插件无法消除，只能不阻塞 UI）；实测值只作为记录，若证明它单独就 ≥800ms，另立 spec。
- **不做虚拟滚动 / 消息列表窗口化**（沿 011 的既有决策）。若实测证明长会话的渲染本身就 >400ms，再单独立项。
- 不做会话内容预取缓存（见开放问题 Q1）。
- 不改队列确认框（005/007）与新建/切换的确认时机；确认框仍是切换链路的第一步。
- 不改会话列表的排序、分页、字段，不改 `sessions.list` 的桥接契约。
- 不把「切换中」做成可取消的长任务（没有可取消的语义：pi 侧已经切了，前端取消只会让状态更乱）。

## 验收口径（用户可感知）

| 场景 | 期望 |
|---|---|
| 有内容的会话里点「新建」并确认 | ≤150ms 内主区域变成新会话空态 + 「正在切换」提示；发送按钮短暂不可用；pi 确认后恢复 |
| 新建时 pi 报错 | 旧对话原样恢复 + 错误项；不出现空对话 |
| 会话列表点某一行 | ≤150ms 内跳到对话页并显示占位；不超过 600ms 内容可读（≤110 条消息的会话）；旧会话消息一帧都不残留 |
| 切换失败 | 回到会话列表 + 错误提示 |
| 流式中切换 | 跳转不被中断动作阻塞；中断生效、新会话不接收旧流 |
| 连续点两行 A→B | 最终落在 B；A 的迟到响应被丢弃 |
| 会话页首次进入 | 列表出现不随历史总量线性劣化（同一项目 100+ 会话、跨 14 个项目目录时仍 ≤500ms） |
| 以上任一场景 | 切换完成后屏幕内容与实际状态一致（无旧帧残留） |

数值阈值汇总（实现与 e2e 的共同事实源，含义见 plan）：

| 指标 | 阈值 |
|---|---|
| T1 点击 → 界面出现可见变化 | ≤ 150ms |
| T2 点击 → 内容区域就绪（占位或实际内容） | ≤ 300ms |
| T3 点击 → 内容可读（≤110 条消息的会话） | ≤ 600ms |
| T4 点击 → 可再次发送 | ≤ 1200ms（含 pi 侧 RPC） |

## 拆分判断（2026-11-10 决策）

**结论：不拆成两份 spec；用 tasks 的两条轨道 + 允许分两批交付来吸收差异。**

理由：

1. **根因链重合**：两条症状共用「等 RPC 才动界面」「缺重绘」「列表重扫」「独立 RPC 串行」四段中的大部分，修法重叠 ≥4/6。拆开就要把同一套埋点、同一张阈值表、同一段 repaint 逻辑写两遍，两边还会各自演化。
2. **阈值必须同一套**：延迟的「可接受」标准是同一个（T1–T4）。分成两份，就会出现「新建 800ms 算通过、切换 300ms 才算通过」这种无法自洽的口径。
3. **风险差异确实存在，但不是 spec 粒度能解决的**：新建轨道只动前端 3 处（乐观清空 + 回滚 + 不 await 列表），风险低、可先进 0.5.7；历史切换轨道可能要碰渲染与 repaint 时序，体量大、需要真机手感验证。这个差异用 **tasks 的 A/B 双轨 + 各自的交付口径**解决更合适。

反过来，**出现以下任一情况就拆**（写在这里，避免以后争论）：

- 实测证明历史切换的瓶颈**主要在消息渲染**且必须引入虚拟滚动 —— 那是独立架构改动，另立 spec。
- 实测证明 pi 侧 `switch_session` / `new_session` 自身就 ≥800ms —— 插件侧的努力有上限，那部分要单独立项（可能要改 pi 的调用方式），不能被本 spec 的阈值含糊掉。
- 用户希望两条分属不同版本发布。

## 开放问题

- **Q1**：是否允许缓存最近 N 个会话的完整消息，让二次切换免掉 `get_messages` 往返？（默认不做：内存与失效复杂度都不小，先看 US1–US3 落地后的实测值）
- **Q2**：新建时输入框是否允许在 pi 确认前就输入（发送仍禁用）？默认允许，避免用户被「整块禁用」打断心流。
- **Q3**：历史切换失败时，是回列表页 + 错误提示（默认），还是留在空白会话里 + 错误提示？
