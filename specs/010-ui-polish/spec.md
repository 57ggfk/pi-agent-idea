# Feature Specification: 界面细节打磨（用户消息紧凑 / 空态居中 / 输入框自适应）

**Feature Branch**: `release/0.5.2`

**Created**: 2026-11-04

**Status**: Draft

**Input**: 用户缺陷清单中的三条：「用户消息框太大，需要紧凑一些」「新会话占位图标等，上下居中对齐」
「添加内容到会话应该自适应输入框高度」。原清单中的「打开历史会话命令详情不能展开」经用户确认**已在 0.5.1 修复**，
从本版范围移除；「发送按钮的下拉」用户尚未决定，本版**不做**（见 Non-goals）。

**难度定位**：本版最轻的一批改动（纯前端 CSS + 一个 autosize 收口），排第一优先，先拿到可验证的小胜。

## 问题陈述

三处都是「每天都在看」的细节，加起来的观感成本远大于单条改动的成本：

| 现象 | 根因（已定位） |
|---|---|
| 一句「好的」占掉一整块气泡，短消息列表看起来又松又长 | `.item-user .item-body` 是 `padding: 8px 12px`，加上消息列的 `gap: 20px` 与 1.55 行高，单行消息高度明显超过内容所需 |
| 空态 π 图标只在水平方向居中，垂直方向贴在顶部附近 | `.empty-state { margin: auto }` 的垂直居中依赖父容器有富余空间，而 `.message-col` 高度由内容决定（`min-height` 未设），没有可吸收的自由空间 |
| IDE 动作、「引用」、`@` 文件、目录注入把文本放进输入框后，框不跟着长高，只能看到两三行 | `autosize()` 只在 `onChange` 与 `pendingPrompt` 一条路径上调用，`insertFile` 等程序化写入没有调用；上限还被写死 160px |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户消息气泡紧凑 (Priority: P1)

用户在密集对话里，希望一条短消息只占它该占的高度。相同内容下，气泡高度要比现在明显更紧，
但文字不得被裁、行距不得挤到一起。

**Why this priority**: 视觉影响面最大（每条用户消息都受影响），改动只在样式层，回归风险最低。

**Independent Test**: 固定内容「好的」发送 → 量 `.item-user` 高度；与改动前基线（记录在 plan）对比，
断言 ≤ 目标值且文字未被裁（`scrollHeight === clientHeight`）。

**Acceptance Scenarios**:

1. **Given** 一条单行用户消息，**Then** 气泡高度 ≤ 32px（含 padding 与边框），文字完整可见。
2. **Given** 一条 5 行用户消息，**Then** 行间距不小于 1.4，文字不被裁切，气泡宽度仍 ≤ 82% 消息列。
3. **Given** 含代码块的用户消息，**Then** 代码块横向不溢出（`scrollWidth === clientWidth`），
   气泡不产生横向滚动条。
4. **Given** 窄窗 360px，**Then** 气泡左右边界都在 `.message-col` 内，不越过 `.app`。
5. **Given** 改动前后的同一条消息，**Then** 高度比 ≤ 0.85（量化「明显更紧」，不是肉眼判断）。

---

### User Story 2 - 空态垂直居中 (Priority: P1)

用户在空会话里看到的 π 图标 + 标题 + 模型名，应当落在消息区的**视觉中心**，而不是贴着顶部。

**Why this priority**: 空态是每次新建会话的第一屏，与 US1 同为纯布局改动，可同批验证。

**Independent Test**: 视口高度 300 / 600 / 900 三档下断言 `.empty-logo` 中心点与消息区中心点差 ≤ 2px。

**Acceptance Scenarios**:

1. **Given** 空会话、视口高 600px，**When** 量 `.empty-logo` 中心与 `.message-list` 可见中心，
   **Then** 垂直偏差 ≤ 2px、水平偏差 ≤ 0.5px。
2. **Given** 视口高 300px（很矮的工具窗），**Then** 图标与文案仍完整可见，不被裁切，偏差 ≤ 4px。
3. **Given** 视口高 900px，**Then** 偏差 ≤ 2px（不随高度漂移）。
4. **Given** 有消息的会话，**Then** 消息从顶部正常开始，不出现「所有消息被垂直居中」的副作用。
5. **Given** IDE 主题切换 light/dark，**Then** 居中结果不变。

---

### User Story 3 - 输入框随内容自适应高度 (Priority: P2)

用户把一段选中的代码「发送给 pi」、或点「引用」把长回复填进输入框时，输入框应当长到能看见这段内容，
而不是只有两三行高、需要自己拖着看。

**Why this priority**: 影响的是「内容注入」这条路径（IDE 动作、引用、@ 文件、后续的目录注入），
比 US1/US2 少一个数量级的触发频次，但它是 0.5.2 其他功能的公共依赖（目录注入也要用）。

**Independent Test**: 通过引用注入 30 行文本 → 断言 textarea 高度 = 内容高度（不超过上限）；
清空发送后回到单行高度。

**Acceptance Scenarios**:

1. **Given** 输入框为空（单行），**When** 触发「Explain with Pi」注入 20 行代码，**Then**
   输入框高度增长到能容纳内容（或到达上限后内部滚动），焦点在文本末尾。
2. **Given** 输入框有内容，**When** 点某条长回复的「引用」，**Then** 高度按合并后的内容重新计算。
3. **Given** 输入框已到高度上限，**When** 继续输入，**Then** 内部出现滚动条，输入框本身不再增高，
   消息列表不被压缩到不可用（消息区高度 ≥ 200px）。
4. **Given** 输入框已增高，**When** 发送消息，**Then** 高度立即回到单行（不是缓慢塌陷，也不残留空白）。
5. **Given** 焦点在输入框、内容是程序化写入的（非用户键入），**Then** 高度与用户手打同样的文本时一致。
6. **Given** 窄窗 360px 与宽窗 900px，**Then** 高度上限按视口比例计算，不会出现「宽窗里只能看两行」。

### Edge Cases

- **超长单行**（无换行符的 5000 字符）：按软换行计算高度，上限内滚动，不得让页面横向溢出。
- **图片 chips 存在时**：chips 占高，输入框仍按文本内容计算，两者叠加不越出 `.app`。
- **流式输出中**：消息区高度在变，输入框高度上限按「当前可用高度」重算，不产生抖动循环。
- **字体加载完成**：字体度量变化后需重算一次高度（`document.fonts.ready`）。
- **输入法组合态**（中文输入）：组合过程中不做高度回弹，避免输入时框上下跳动。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 单行用户消息气泡高度 MUST ≤ 32px，且文字 MUST NOT 被裁切。
- **FR-002**: 用户消息气泡的紧凑化 MUST 通过 padding / 行高 / 气泡宽度实现，
  MUST NOT 通过缩小字号或裁切文本实现。
- **FR-003**: 紧凑化后 MUST NOT 引入横向溢出（气泡、代码块、`.message-col` 三者 `scrollWidth === clientWidth`）。
- **FR-004**: 空态 MUST 在消息区同时水平与垂直居中；水平偏差 ≤ 0.5px，垂直偏差 ≤ 2px（视口高 ≥ 400px 时）。
- **FR-005**: 空态居中 MUST NOT 影响有消息时的布局（消息仍从顶部排列）。
- **FR-006**: 所有把文本写入输入框的路径 MUST 在写入后重新计算高度：
  IDE 动作注入、引用、队列取回、`@` 文件补全、目录注入、编辑回填。
- **FR-007**: 输入框高度上限 MUST 为 `min(320px, 45% × 视口可用高度)`；超过上限时内部滚动，
  且消息区高度 MUST ≥ 200px。
- **FR-008**: 发送后输入框 MUST 立即回到单行高度。
- **FR-009**: 输入法组合输入期间 MUST NOT 触发高度回弹。
- **FR-010**: 上述规则 MUST 在 360 / 430 / 900px 三档宽度下同时成立。

### Key Entities

- **输入框高度策略**：`measure(textarea) → clamp(scrollHeight, minHeight, cap(viewport))`，单一实现，所有写入路径复用。
- **紧凑基线**：改动前后的气泡高度对照表（plan 记录实测值，tasks 断言比例）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同样一段对话，滚动一次能看到的消息条数增加 ≥15%（用固定 20 条消息的 fixture 量首屏条数）。
- **SC-002**: 空态图标在 300/600/900px 三种高度下中心偏差 ≤ 2px，且不随窗口拉伸漂移。
- **SC-003**: 「注入 20 行代码」到「完整看见这 20 行」的操作从「拖拽调整/滚动」变为 0 步。
- **SC-004**: `web/e2e/layout-regressions.spec.ts` 既有断言全绿，并新增本 feature 的三组断言。

## Non-goals

- **发送按钮右侧下拉（Send now / Steer / Follow-up）**：用户尚未决定交互形态，本版不改动，
  也不做「空闲时隐藏」这类半成品。
- **历史会话命令卡片展开**：0.5.1 已修复，本版不复测、不改动（若回归则为独立缺陷）。
- **消息字体/字号体系调整**：只调间距与气泡，不改字号基线，避免影响行数与既有断言。
