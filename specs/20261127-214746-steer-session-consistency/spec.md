# Feature Specification: 插话在队列与会话之间的一致性

**Feature Branch**: `[20261127-214746-steer-session-consistency]`
**Created**: 2026-11-27
**Status**: 已实现（2026-11-28；T1–T5 见 [./tasks.md](./tasks.md)）

**GitHub Issue**: [#8](https://github.com/57ggfk/pi-agent-idea/issues/8)

**Input**: 用户描述——「第二消息既进队列又进会话，这一条在没有完全插进 Agent 轮次里面的时候，
应该是可编辑状态，如果插进去了之后队列里应该就消失了。现在的问题是，在没插进去的时候，
会话里有，然后在队列里点了编辑之后，会话里还留着呢。那我编辑完再发送的话，就又变成了一条，
原来在会话里那一条还在，也不知道插进去了没有。那我觉得既然都点了重新编辑了，
是不是应该把插进会话的那条撤回来。」

## 背景：同一条插话同时存在于两个地方

pi 的插话（steer）语义：**注入正在运行的轮次**。pi 把注入的 steering 文本记为
一条真正的 user message。

插件为了即时反馈（等 transcript 回放要 1–2 秒），在 fire 的瞬间就往会话里插一条
`ephemeral: true` 的 user item，带「插话」标记（spec 005 plan §5 原文：
「不这样做就会重复渲染：pi 会在下一轮把这条 steering 消息记为真正的 user 消息」）。

于是**同一条插话文本同时存在于两处**：

| 位置 | 是什么 | 生命周期 |
|---|---|---|
| **队列**（输入框上方的 QueueBar） | 插件的镜像条目，带 id / 图片 / 模式 | pi 注入后由 `queue_update` 对齐掉 |
| **会话**（消息流） | fire 时插的 ephemeral item（本地造的），下一次 `replayMessages` 时被丢弃 | 只活到下一次 replay |

## 缺陷（用户描述的现象）

1. **取回后，会话里那条不撤**：在队列里点 ✎（取回），队列条目移除、文本回填输入框，
   **会话里那条 ephemeral item 还在**，带着**旧文本**。编辑完发送 → 会话里出现**两条**
   （旧的原文 + 新的编辑后文本）。
2. **看不出插没插进去**：ephemeral item 只有「插话」一个标记，**不区分「还在队列里」
   和「已经被 pi 注入」**。用户无法判断现在这条是不是已经生效了。

用户提出的原则：**既然点了重新编辑，就该把插进会话的那条撤回来。**

## 用户场景与验收

### User Story 1 — 取回即撤回（Priority: P1）

**为什么重要**：用户在编辑一条还没生效的插话时，会话里留着旧文本 → 编辑后发送 →
会话里两条。用户在跟自己的会话打架，且无从判断哪条才是生效的那条。

**独立可测**：插话 → 在队列点 ✎ 取回 → 编辑 → 发送 → 会话里只有一条（编辑后的）。

**验收场景**：

1. **Given** 一条还在队列里的插话，**When** 点 ✎ 取回，
   **Then** 会话里那条对应的 ephemeral item **消失**，输入框收到文本
2. **Given** 同上，**When** 取回后不编辑、直接发送，
   **Then** 会话里只有**一条**用户消息（编辑后的），没有重复
3. **Given** 一条**已被 pi 注入**的插话，**When** 点 ✎ 取回，
   **Then** 行为明确：要么该条目已不在队列（取不到）、要么给出「已注入、无法取回」的
   明确提示 —— **不得**把已注入的消息静默撤回（pi 的上下文里已经有它了）

### User Story 2 — 看得出插没插进去（Priority: P1）

**为什么重要**：现在那条「插话」标记只说明「这是插话」，不说明「它还在队列里、
尚未注入」还是「它已经被 pi 收下了」。用户据此做决定（要不要改、改了算不算），
信息不够就只能猜。

**验收场景**：

1. **Given** 一条已 fire、pi 尚未注入的插话，**When** 看消息流，
   **Then** 它带着「**排队中**」的可见标记
2. **Given** 同一条插话被 pi 注入后，**When** 看消息流，
   **Then** 标记变成「**已插话**」（或等价的已生效状态），与上一条**视觉上可区分**
3. **Given** 上述两种状态，**When** 用户决定是否编辑，
   **Then** 能从标记判断出「还在队列里（可编辑）」还是「已注入（不可编辑）」

## 需求（Functional Requirements）

- **FR-001**：从队列取回一条插话时，**会话里对应的临时条目必须同步撤回**，
  不得留下旧文本。
- **FR-002**：取回后编辑并发送，会话里**不得**出现同一条消息的两份。
- **FR-003**：插话条目必须能区分「**排队中**」与「**已注入**」两种状态，且状态变化
  在消息流里可见。
- **FR-004**：已注入的插话**不得**被静默撤回（pi 上下文里已有它）—— 要么取不到，
  要么明确告知。
- **FR-005**：单实例 / 无队列时的行为不变。

## 关键设计取舍（待拍板）

- **「会话里那条」到底是什么**：
  - 候选 A：fire 时插的 ephemeral item（本地造的，还没进 pi 的 transcript）
  - 候选 B：pi 已经记下的真实 user message（下一轮 replay 后 ephemeral 被丢弃、
    真实那条出现）
  - 取回发生在「还没注入」时 → 撤的是 A；已注入 → 撤不掉的是 B（FR-004）。
  **所以撤回必须按状态分别处理**，不能一刀切。
- **「已注入」怎么判定**：pi 的 `steer` 响应只有 `{disposition:"queued"}`，
  **不是注入确认**（spec 005 实测基线 6）。真源是 pi 的 `queue_update`：
  文本从 `steering` 数组里消失 = 已被消费。所以判定依据是
  **该文本是否还在 pi 的 steering 数组里**——插件的镜像已经有这个信息。
- **临时条目要不要保留**：如果 pi 已注入，ephemeral 会被 replay 丢弃、真实那条出现；
  如果没注入，ephemeral 一直留着。此时用户看到的是「一条带插话标记的消息」，
  但它**还没生效**——这正是 FR-003 要解决的歧义。

## 非目标

- 不改 pi 的插话语义（什么时候注入、注入几条）。
- 不做「撤回已注入的消息」——pi 上下文里已经有了，撤不掉。

## 边界与风险

- **队列与会话是两份状态**：插件靠文本对齐（pi 的 `queue_update` 只给文本数组，
  没有 id），所以「同一条」只能靠文本认——改文本就等于换了一条。
- **replay 会清掉 ephemeral**：取回后如果恰好发生一次 replay，临时条目会被丢弃，
  撤回逻辑要幂等。
- **跨端契约**：若消息 item 增加状态字段（如 `queued` / `injected`），
  `web/src/store/types.ts` 与 Kotlin 侧必须同一次改动里改。

## 假设与依赖

- pi 的 `queue_update` 会持续推送 steering 数组的真实内容（spec 005 实测基线 1）。
- 消息流里的插话条目由插件 fire 时插入，pi 不认识它。
